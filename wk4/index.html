Authentication vs Authorization: Passwords and Hashing

Almost every real app has accounts. The moment you add accounts, you take on two separate jobs, and mixing them up is the source of a lot of real-world security bugs. Keep the two questions apart from the very start:

Authentication — “Who are you?”

Authentication is proving your identity. You claim to be a user, and the app checks something only that user should have — usually a password. If the proof checks out, the app believes the claim. Logging in is authentication.

Authorization — “What may you do?”

Authorization is deciding what an already-identified user is allowed to do. You can be fully logged in and still not be allowed to see another student’s grades, edit a course, or open the admin page. Authorization always comes after authentication.

Think of a building badge. Showing your badge at the front desk and having the photo match your face is authentication: the building now knows who you are. Which doors that badge actually unlocks — the lobby, your floor, the server room — is authorization. A valid badge gets you identified everywhere, but it only opens the doors you were given permission for. Your app works the same way: first it identifies the visitor, then it checks each door separately.

Why you never store a plain password

A password is a secret word or phrase that only the account owner should know. The obvious way to support logins is to store each user’s password in the database and compare what they type against it. Do not do this. Databases leak: a backup file gets shared, a misconfigured server exposes a table, an attacker finds an injection bug (Section 4.5). If your table holds plain-text passwords, one leak hands out every account at once — and because people reuse passwords, it hands out their email and bank accounts too.

The fix is to store something you can check a password against without storing the password itself. That something is a hash.

A hash is a one-way fingerprint of some data. You run the password through a hash function — a recipe that scrambles input into a fixed-size string of characters — and you store the result. The important properties are:

  • One-way. You can turn a password into its hash, but you cannot turn the hash back into the password. There is no “unhash” button.
  • Deterministic. The same input always produces the same hash, so checking a login attempt is easy: hash what the user typed and compare it with the stored hash.
  • Completely different for a tiny change. Change one letter and the hash looks nothing alike, so a hash reveals nothing about how close a guess is.

At login you never recover the real password. You hash the attempt and compare fingerprints. If they match, the attempt almost certainly came from someone who knows the password — and your database never held the password itself.

The salt: one random extra ingredient per user

Hashing alone has a weakness. Two users who both chose hunter2 would get the same hash, and an attacker who pre-computes hashes for common passwords (a precomputed list is often called a rainbow table) can match them in bulk.

A salt fixes that. A salt is a random value generated fresh for each user and mixed into the password before hashing. That randomness must come from a cryptographic random source — in the demo below, crypto.randomBytes — never from a counter, a timestamp, or the username, all of which an attacker can predict or guess. You store the salt right next to the hash — the salt is not a secret — and you use it again at login time. Now two users with the same password store completely different values, and precomputed tables are useless because every user’s mixture is unique.

Read the code once more, slowly. hashPassword returns one string, salt:hash, and that single string is all you save in the database. checkPassword splits it back apart, re-hashes the attempt with the same salt, and compares. One detail worth copying into your own code: never compare the hashes with ===. Verification uses crypto.timingSafeEqual, which takes the same amount of time whether the values match early or late, so the comparison does not leak how much of a guess was right through timing — an attacker cannot learn the hash byte by byte by measuring response times.

One simplification to notice: the demo uses scryptSync, the synchronous (blocking) form of scrypt, to keep the code short. In a real server you would use the asynchronous form of scrypt (or a library that does the same), because the sync version freezes the event loop — while one password is being checked, every other visitor waits, which is the Week 1 event-loop problem returning in a new place.

Here is that asynchronous pair, in a file of its own. It is the version the login route in Section 4.2 uses, so treat hash-demo.js as the warm-up and this as the real thing.

Three things changed. promisify turns Node’s callback-style crypto.scrypt into a function you can await, so both helpers are now async and every caller has to await them. The last line exports the pair so a route file can require it. And there is a COST object, which the demo did not have.

scrypt is slow on purpose, and COST sets how slow. N is the cost parameter: double it and every guess takes twice the time and twice the memory. Leave the options out, as hash-demo.js does, and Node uses N = 16384, r = 8, p = 1 — fine for a demo, but below what current guidance asks for. The OWASP Password Storage Cheat Sheet, the standard reference for this decision, sets the bar for scrypt at “a minimum CPU/memory cost parameter of (2^17), a minimum block size of 8 (1024 bytes), and a parallelization parameter of 1” — the first three numbers in COST, where 2 ** 17 is JavaScript for 2 to the power 17. The fourth, maxmem, is there because Node refuses an N that large until you raise its memory limit: one hash at these settings needs about 128 MiB. (On the machine this code was tested on, one hash took about 20 milliseconds at Node’s default and about 170 at these settings.) Whatever settings you choose, hash and check with the same ones: a stored hash made with one N never matches a check run with another.

And the check that runs at every login, using exactly those parts:

  1. Look up the row by username and split password_hash at the colon into its salt and its hash.
  2. Run scrypt on the password that was just typed, using that stored salt and the same 64-byte key length.

Keep the division of labor clear: the browser makes typing a long 15-character passphrase comfortable (offering Show/Hide and a live counter), HTTPS encrypts the password on the wire, and Node's hashPassword() generates the random salt and slow scrypt hash on the server before anything touches the database.

Students often ask why the app does not simply encrypt the passwords instead. The tabs below draw the line, because the difference decides whether a leak is embarrassing or catastrophic.

One-way, on purpose. Hashing turns a password into a fingerprint and throws the password away. There is no key and no reverse operation. At login you do not recover anything: you hash the new attempt and compare fingerprints. If your table leaks, the attacker gets fingerprints — useless for logging in directly, and expensive to guess against because a password hash like scrypt is deliberately slow.

Two-way, by design. Encryption scrambles data so that whoever holds the key can unscramble it. Your server would need the key at login time, which means the key lives somewhere the server can reach — and an attacker who compromises the server can usually reach it too. One key plus one leaked table equals every password, recovered. Anything that can be reversed eventually will be.

Passwords are verified, never recovered. A well-built app genuinely cannot tell a user what their password is — that is why real sites offer “reset your password” and never “email me my password.” If a site can show you your old password, it stored it reversibly, and you have learned something alarming about that site.

Never invent your own password scheme

This demo uses Node’s built-in scrypt so you can see every moving part. bcrypt, scrypt and Argon2id are all legitimate password hashes that you will meet in working code, and the OWASP cheat sheet ranks them: Argon2id first, scrypt when Argon2id is not available, bcrypt for older systems. In a real project, either keep scrypt — in its asynchronous form, with the cost settings from password.js — or move to Argon2id, which no longer needs a package from npm: Node now builds it in as crypto.argon2. Never store passwords in plain text, never use a fast general-purpose hash like MD5 or SHA-256 alone for passwords, and never try to “encrypt” passwords — encryption can be reversed by anyone who finds the key, which is exactly the problem hashing avoids.

Sessions and the Login Flow

In Week 3 you met the problem underneath everything in this section: HTTP is stateless, which means each request arrives with no memory of the requests before it. A session is the server’s fix — a small record the server keeps about one visitor, identified by a random session ID. Your browser carries that ID in a cookie (a small name-and-value pair the browser stores and sends back automatically), and the server uses it to look your record up on every request.

You already ran the smallest possible session demo in Week 3. Here it is again, exactly as it was, because the login flow is this same machine with one extra job: remembering who the session belongs to.

$ curl -c jar.txt http://localhost:3000/count (first visit, saves the session cookie) Visit number 1 $ curl -b jar.txt http://localhost:3000/count (same browser jar) Visit number 2 $ curl -b jar.txt http://localhost:3000/count Visit number 3 $ curl http://localhost:3000/count (no cookie: a new session) Visit number 1 --- server console --- Listening on port 3000

Notice what the cookie holds: only the session ID. The visit count itself never leaves the server. That split — an unguessable ID in the browser, the real data on the server — is what makes sessions safe enough to carry login state.

The login flow, step by step

Logging in is just a session that gets a name attached to it. Step through the whole exchange:

1 · FormYou submit a username and password over HTTPS.
2 · CheckThe server hashes the attempt and compares it with the stored hash.
3 · SessionThe server creates a session and stores your user ID in it.
4 · CookieThe response sets a cookie holding only the session ID.
5 · RecognizedLater requests send the cookie, so the server knows it is still you.
6 · LogoutLogout destroys the session on the server. The old ID stops working.

  1. You submit credentials. Credentials are the proof you present to log in — here, a username and a password, sent in a POST request. This step is why login pages must use HTTPS (Section 4.5): the password travels in this request.

  2. The server checks the hash. The server looks up the stored salt:hash value for that username and runs the checkPassword function from Section 4.1. If there is no such user, or the check fails, the answer is a generic “wrong username or password” — never say which half was wrong, because that tells an attacker which usernames exist.

  3. A session is created. On success the server creates a fresh session and stores the user’s ID (and usually their role, Section 4.4) in it. “Fresh” matters: the server throws away any session ID the browser had before login and issues a new one, so an old ID planted by an attacker cannot be reused. This is called regenerating the session.

  4. The cookie carries the ID. The server’s response includes a Set-Cookie header with the new session ID. From here on, your browser attaches that cookie to every request to this site without you doing anything.

  5. Later requests are recognized. The session middleware reads the cookie, loads the session record, and your route handlers can read req.session.userId to know who is asking. No password is sent again — the session ID stands in for it until the session ends.

  6. Logout destroys the session. Logging out deletes the session record on the server, not just the cookie in the browser. Anyone holding a copy of the old session ID finds it worthless, because there is nothing left for it to unlock.

Expected behavior (this assembled example was not captured as a single run — it combines the verified pieces above):

  • The same request with a wrong password — or an unknown username — returns 401 with the same generic message either way, after the same amount of work.
  • A request with the password missing, or with no body at all, gets that same 401 too — never a crash.
  • While the session lives, requests arrive with req.session.userId and req.session.role already filled in.
  • After POST /logout, the old session cookie no longer identifies anyone, because the server-side record is gone.

Step 2 of the flow promised never to reveal which usernames exist. Two parts of the route are there only to keep that promise, because a server can leak the answer without saying a word:

  • Bad input gets the ordinary 401. The typeof check runs before anything else, so a missing password, an empty body, or a field that is not text gets the same answer as any other failed login. Without it, checkPassword throws when the password is missing and Express answers 500. A login route that crashes on some requests and answers 401 on others is handing out clues, and in the most common version of this bug the crash happens only when the username is real. (The || {} is there because in Express 5 req.body is undefined when no body was parsed.)
  • The slow check always runs. If the route skipped hashing for unknown usernames, they would answer faster than real ones, and a stopwatch would be enough to tell them apart. DUMMY_HASH is a real hash of a random password nobody knows, made once when the server starts. An unknown username is checked against it, so the request takes just as long and still fails.

The cookie block has grown too. The Week 3 demo already set httpOnly and sameSite; a login adds a lifetime and an HTTPS mark. On its own, express-session sets only httpOnly, so each of the other three is a decision you make:

  • httpOnly: true keeps the cookie out of reach of JavaScript in the page, so an XSS bug (Section 4.5) cannot read the session ID.
  • sameSite: 'lax' tells the browser to leave the cookie off a cross-site POST, such as a hidden form on another site that submits to your app, while still sending it when someone follows an ordinary link to you — the first CSRF defense in Section 4.5.
  • maxAge is the cookie’s lifetime in milliseconds — here two hours — after which the visitor has to log in again; without it the cookie has no time limit and lasts until the browser closes.
  • secure: 'auto' marks the cookie HTTPS-only whenever the request arrived over HTTPS, and leaves the mark off on plain http://localhost so that logging in still works while you develop.

Three session rules that are not optional
  • Regenerate at login. Always replace the session ID when a visitor logs in, as the code above does, so a pre-login ID can never become a logged-in ID.
  • The secret comes from the environment. The secret signs session cookies so visitors cannot forge them. The Week 3 demo hard-coded 'dev-secret-change-me' so you could read it, and said so in a comment; real apps read it from an environment variable (Section 4.5) and never commit it to Git.
  • Never store the password in the session. Store the user ID and role. The session is not the place for passwords, hashes, or anything else you would not want exposed if a session record leaks.
The secure-cookie trap: when login never sticks

The cookie’s secure option means “HTTPS only.” Set it to true, and whenever the server believes a request did not arrive over HTTPS, express-session simply leaves the Set-Cookie header out of the response. There is no error and no warning. The browser never receives a cookie, every request looks like a new visitor, and login “mysteriously” never sticks.

That happens in two places. On plain http://localhost the server is right: the connection is not HTTPS. On a hosting platform the server is wrong, which is harder to spot. The platform’s proxy handles HTTPS and passes each request on to your app over plain HTTP, so your app sees HTTP even though the visitor used HTTPS. The fix is one line before the session middleware, app.set('trust proxy', 1), which tells Express to believe the proxy’s report of how the request really arrived. Add it only when a proxy really does sit in front of your app.

secure: 'auto', used in the route above, avoids the trap in both places: the cookie is always sent, and it is marked HTTPS-only whenever Express sees HTTPS. You still want the trust proxy line on a host. Without it Express never sees the HTTPS, and the cookie goes out unmarked.

How long does a session live?

A session is not forever, and it should not be. Two different endings are normal:

  • Logout ends it immediately, as you saw in step 6: the record is destroyed and the ID becomes worthless at once.
  • Expiry ends it quietly. Session middleware can give each session a maximum lifetime — the two-hour maxAge in the route above — and many apps also end a session after a period of inactivity. That is why a site you left open overnight asks you to log in again in the morning — the session aged out, which limits how long a copied session ID stays useful to anyone else.

Keep the two halves straight, because beginners constantly swap them:

Lives in: the browser. Contains: the session ID, and nothing else of value. Travels: automatically, on every request to the site that set it. If it is copied: the copier can present the ID and be treated as that session until the session is destroyed or expires — which is why session cookies must only travel over HTTPS.

Lives in: the server (in memory in the demos; in a store or database in larger apps). Contains: whatever your code puts there — here, userId and role. Travels: never. If the server restarts: the default in-memory store forgets every session and everyone is logged out — acceptable for a class project, and the reason production apps use a persistent session store.

Tokens and JSON Web Tokens

Sessions ask the server to remember you. A token takes the opposite approach: a token is a string the server hands you after login that carries proof of who you are, signed so the server can check it later without remembering anything. You present the token with each request, the server verifies the signature, and if the signature is valid it trusts what the token says. Nothing is stored on the server between requests.

Why have both? Sessions fit classic server-rendered apps, where one server serves its own pages. Tokens fit APIs: a mobile app, a single-page app, or several different servers can all accept the same token, because verifying it needs only the secret — no shared session store. You will meet both in real jobs, so this week you learn the token format the industry standardized on.

A JSON Web Token (JWT, pronounced “jot”) is a token format built from JSON. A JWT has exactly three parts, joined by dots:

1 · Header

A small JSON object saying what kind of token this is and which signing algorithm was used — here, HS256.

2 · Payload

A JSON object with the claims — the facts the token asserts, such as who the user is (sub) and their role. The payload also carries iat (issued at) and exp (expires at) timestamps.

3 · Signature

A value computed from the header, the payload, and a secret key only the server knows. Change even one character of the payload and the signature no longer matches.

The header and payload are not encrypted. They are Base64URL-encoded — rewritten in a URL-safe alphabet so the token can travel in headers — and anyone can decode them, as you will do yourself in a moment. The signature is the only thing protecting the contents, and it protects them against changes, not against reading.

Decode one yourself

Prove the “anyone can read it” claim. This playground runs only in your browser, and there is no secret anywhere in it. Be blunt about what you just did: decoding a token proves nothing. Anyone can decode any token, including a forged one that was never issued by your server — you just decoded one that claims to be an admin — so a decoded payload is just a claim written by whoever handed you the token. The payload only becomes trustworthy after the server verifies the signature with its secret — that verification, not the decoding, is what earns trust.

Signing is not encryption

You just read a signed token’s payload with three lines of code — no secret, no permission. A signature proves a token was issued by your server and has not been changed since. It hides nothing. Never put anything private in a JWT payload: no passwords, no hashes, no personal details you would not print on a poster. Keep payloads to IDs, roles, and timestamps.

One payload claim deserves its own sentence. exp is the expiry time, written as a Unix timestamp (seconds since 1 January 1970). In this token, exp is exactly 3,600 seconds — one hour — after iat, because the demo signed it with expiresIn: '1h'. After that moment, jwt.verify rejects the token even though its signature is genuine.

Expiry matters more for tokens than for sessions, and the reason is the real trade-off between the two. A session can always be cancelled: destroy the record on the server and its ID stops working at once. A JWT has no record to destroy. The server can refuse one early only by keeping some state after all — a denylist of revoked tokens that it checks on every request — or by changing the secret, which rejects every token it ever issued. Expect two consequences. Logging out only makes the client forget its token; a copy of that token still verifies until exp. And the role claim stays whatever it was when the token was signed, so a user who is demoted from admin keeps a working admin token until it expires. Short lifetimes are how token-based apps keep both of those windows small.

How a token travels

After login, the client keeps the token and presents it on every request, conventionally in the Authorization header, in this exact shape:

The word Bearer means “whoever bears (carries) this token” — the server does not ask for anything else. Middleware on the server reads the header, runs the same verify you saw in the demo, and — if it passes — copies the claims onto the request (often as req.user), so route handlers and role guards can use sub and role exactly the way the session version used req.session. Same authorization logic, different delivery van.

“The client keeps the token” hides a real decision when the client is a browser. Put the token in localStorage and any script running on your page can read it, so one XSS bug (Section 4.5) lets an attacker copy the token and use it from their own machine. Put it in an HttpOnly cookie instead and page scripts cannot read it — but now the browser attaches it to requests automatically, which brings CSRF back and makes SameSite matter again. For this course’s app, where one server sends both the pages and the API, sessions are the simpler choice: the same cookie protections, and nothing for your own script to store.

Authorization: Roles and Protected Routes

Authentication told you who is asking. Now the server has to decide, on every route that matters, whether this user may do this thing. The standard way to organize those decisions is a role: a named level of permission attached to an account, such as student, instructor, or admin. Each user gets one role when their account is created — chosen by your server, never by the person signing up. You store it with their account (and copy it into their session or token at login), and write each route’s rule in terms of roles instead of individual names.

In a course app, who…StudentInstructorAdmin
Views course pagesYesYesYes

Submits homeworkYesYesYes

A table like this is called a permission matrix: actions down one side, roles across the top, and a yes or no in every cell. Writing it down before you code is not paperwork — it is the authorization design. Every guard you write next is just one cell of this table turned into code.

Every account starts at sign-up, and sign-up is where roles are most often given away by accident. A sign-up form sends a username and a password. If the route also reads a role out of the same request, anyone can add role=admin to what they send and promote themselves, with no password guessing required. 401 vs 403: two different kinds of “no”

The guards above answer with two different status codes, and using the right one matters to the client on the other end:

  • 401 Unauthorized — “You have not proven who you are.” Nobody is logged in (or the session or token is invalid), so the app cannot even start the permission question. The usual client response is to show a login page. Despite its name, 401 is about authentication.
  • 403 Forbidden — “I know exactly who you are, and you still may not do this.” The user is authenticated, but their role does not allow this action. Showing a login page would be pointless; they are already logged in.

Hide it in the UI and enforce it on the server

It is good design not to show a student an “Enter grades” button they cannot use. It is not security. Least privilege: give each role only what it needs

When you fill in your own permission matrix, work by one rule: least privilege — every role gets the smallest set of permissions that lets it do its job, and nothing more. A student role that can also edit grades “just in case” is not convenient; it is a bug waiting for a curious student. Start every cell at no, and make each yes earn its place by naming the real task that needs it. If nobody can name the task, the answer stays no.

Roles are coarse, though — “members may edit” is not enough on its own, because it does not say whose records a member may edit. The server also checks ownership: a member may edit only their own records, by comparing the record’s owner id with the signed-in user’s id from the session (req.session.userId). For example, a student in the course app may edit a book on their own list, but if they change the id in the request to reach another student’s book, the owner ids will not match and the server must refuse. An instructor or admin role is the exception: that role may touch everyone’s records, because reviewing and managing the whole class is its job.

Security Hygiene: HTTPS, Secrets and Common Attacks

This section is enrichment: five habits that sit underneath everything else in this week. None of them is a big feature. All of them are the difference between a class project and an app you could responsibly put in front of real users. Treat them as a pre-flight checklist you run on every project from now on.

1 · HTTPS: a sealed envelope instead of a postcard

Plain HTTP sends requests and responses as readable text. Anyone positioned along the path — a compromised router, a hostile Wi-Fi hotspot — can read them, including passwords and session cookies, and can even change them in transit. HTTPS is HTTP carried inside TLS (Transport Layer Security), which encrypts the connection: the two sides agree on keys at the start, and everything after that is scrambled to everyone in between. The server also proves its identity with a certificate, a digitally signed ID card issued by a trusted authority, so your browser knows it reached your real server and not an impostor.

For this course the practical rules are simple: logins and sessions must never travel over plain HTTP, hosting platforms enable HTTPS for you (usually with free certificates), and on your own server you redirect every HTTP request to its HTTPS address. A session cookie sent over plain HTTP is a house key mailed on a postcard.

Example — what someone listening on the café Wi-Fi sees when Ada logs in:

Over plain HTTP, the whole login request is readable text, password included:

POST /login HTTP/1.1 Host: example.com Content-Type: application/x-www-form-urlencoded username=ada&password=hunter2

Over HTTPS, the same request crosses the same network as TLS ciphertext — no readable method, headers, or body (illustrative bytes):

Only the two endpoints — Ada’s browser and the real server, whose identity the certificate vouched for — can turn the second version back into the first.

2 · Secrets live in environment variables, never in code

A secret is any value that grants power: a session-signing secret, a JWT secret, a database password, an API key. You met the pattern in Week 3 and used it in Section 4.2: the code reads the value from an environment variable — a setting supplied by the machine the program runs on, not written in the source.

Why the fuss? Code gets copied: into Git, onto teammates’ laptops, into error reports. A secret committed once stays in the repository’s history even after you delete the line. Environment variables keep the secret in exactly one place — the server’s configuration — and let every developer use a different throwaway value on their own machine. If a real secret ever does leak, the fix is to rotate it: generate a new one, deploy it, and the leaked value becomes worthless.

A secret also has to be long and random — not a word, a phrase, or anything else a person made up. Anyone who captures a single JWT can test guesses against its signature on their own machine, as fast as their hardware allows, without ever touching your server; if the secret is guessable, they can then sign any token they like. This section adds only the rule: if a value would grant power to whoever holds it, it belongs in the environment, never in the source.

3 · SQL injection — and why Week 3’s placeholders stop it

SQL injection is an attack where a visitor types database commands into an ordinary form field and a careless server runs them. It happens when code builds a query by gluing strings together:

What the database actually receives from the vulnerable version, when the username field contains ' OR '1'='1:

SELECT * FROM users WHERE name = '' OR '1'='1'

The attacker’s first quote closes the name string early, and the rest of the input becomes part of the condition. '1'='1' is always true, so the WHERE clause matches every row in the table — the query the server meant to run for one user now runs for all of them. With the placeholder version in the safe code above, that same input is compared, as data, against actual names, matches nobody, and changes nothing.

The placeholder is the whole defense, and it is structural: with placeholders, the database receives the query shape and the values through separate channels, so a value can never rewrite the query — even if it contains quotes, SQL keywords, or an entire second statement. The rule is absolute: never build SQL by joining strings with user input; always use placeholders (or your library’s equivalent). MongoDB has no SQL string to break, but that does not make it safe by default. It needs a rule of its own — every value that goes into a query must be the type you expect — and the NoSQL injection item in the checklist below shows why.

4 · XSS: user content is data, not code

Cross-site scripting (XSS) is the front-end cousin of injection: an attacker stores a piece of JavaScript as ordinary content — say, in a comment or a display name — and your page later inserts it into the HTML as markup instead of text, so it runs in every visitor’s browser, with their session. The defense mirrors the back-end rule: treat everything a user typed as data. Escape it when you insert it into a page (turning < into &lt; so the browser shows it instead of obeying it), prefer textContent over innerHTML in your own scripts, and let your framework or template engine escape by default. This course’s own components follow the rule — it is why the authoring guide escapes text in interactive activities.

5 · Keep dependencies updated

Your app stands on packages you did not write, and vulnerabilities are found in popular packages regularly. Node ships with a scanner for exactly this: running npm audit in a project compares your installed dependency versions against a database of known vulnerabilities and reports what it finds, with suggested fixes (often npm audit fix, or updating the package yourself). Be honest about what it is: npm audit is a scanner, not a shield. It can only flag problems that are already known and catalogued, and a clean report does not prove your app is secure. Run it before every deployment anyway — it catches the known, fixable problems, which are the embarrassing ones to ship.

Example — what an audit report with something to fix looks like (illustrative sample — your packages, versions and counts will differ):

$ npm audit # npm audit report example-lib <2.0.0 Severity: high: example-lib vulnerable to prototype pollution node_modules/example-lib fix available via `npm audit fix` 1 high severity vulnerability To address all issues, run: npm audit fix

One flagged package, a plain statement of the problem, and the suggested fix — that is the whole interaction. Run the fix (or update the package yourself), then run npm audit again to confirm the report is clean before you deploy.

Four more habits on the same checklist

  • Watch for CSRF Cross-site request forgery (CSRF) is an attack where a malicious page tricks your browser into sending a request to a site you are logged into, and your browser helpfully attaches your session cookie, so the request looks like yours. First defenses are SameSite cookies (Lax or Strict, from Week 3), which limit when cookies travel with cross-site requests, and a simple rule: never change anything important in response to a GET request.
  • Throttle login attempts Without a limit, an attacker can guess passwords as fast as the server answers — thousands of tries before you notice. Slow them down: delay responses, or temporarily lock an account, after repeated failed logins. Libraries such as express-rate-limit exist for exactly this, so you do not have to build the counting yourself.
  • Never send hashes back An API response must never include the stored password hash, or the salt that goes with it. Leave those fields out of every user object you return, even to the account owner themselves. A hash handed out in a response is a hash an attacker can take away and guess against offline, at their leisure.
  • Watch for NoSQL injection If a login route feeds a JSON body straight into a MongoDB query, an attacker can send an object instead of a string: a username of {"$ne": null} means “not equal to null” as a query condition, and can match the first user in the database. The defense is the Week 3 rule applied again: check the type of every value — here, that the username and password really are strings — before it goes into a query.

  • HTTPS everywhere it matters Logins, sessions and tokens never travel over plain HTTP.
  • No secrets in code or Git Session secrets, JWT secrets and database passwords come from environment variables.
  • Placeholders for every query User input is always data, never part of the SQL string.
  • Escape user content Anything a user typed is inserted into pages as text, not markup.
  • npm audit before deploying Known vulnerabilities in dependencies get fixed before users arrive.
