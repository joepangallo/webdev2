Routing in Depth: Parameters and Query Strings

A route is a rule that says: when a request with this method arrives at this path, run this function. In Week 1 your routes were fixed addresses like /about. Real sites cannot work that way. A shop with 10,000 products cannot have 10,000 route functions, one per product. It needs one route that captures which product the URL names.

Express gives you two different places to pull values out of a URL, and choosing the right one is a design decision you will make constantly:

  • A route parameter is a named placeholder inside the path itself, written with a colon, like /users/:id. It identifies which thing the request is about. The value is part of the address: remove it and the address points somewhere else, or nowhere.
  • A query string is the part of the URL after a ?: a list of key=value pairs joined by &, like ?name=Ada&plan=pro. It carries options for the request: a search term, a page number, a sort order. Remove it and the address still names the same page, just with default options.

Here is the rule of thumb: if the value says which resource it is, make it a parameter. If the value tunes how the resource is delivered, make it a query string. /users/42 names user 42. /users?sort=name names the user list, sorted one particular way.

Real output — captured by running this exact program (Node 26, Express 5):

$ curl "http://localhost:3000/greet?name=Ada" {"message":"Hello, Ada!"} $ curl http://localhost:3000/greet {"message":"Hello, stranger!"} $ curl http://localhost:3000/users/42 {"userId":"42"} --- server console --- Listening on port 3000

The first two requests hit the same route. The query string never changes which route matches; it only changes what the handler finds in req.query. The third request shows a parameter doing the opposite job: /users/42, /users/7 and /users/ada all match the one route /users/:id, and the handler learns which user from req.params.id.

Three places values hide: a map

By the end of this week, a handler can receive values from three different places, and beginners constantly mix them up. Keep this map next to you:

SourceWhere it lives in the requestHow the handler reads itExample
Route parameterInside the path, filling a :placeholderreq.params.id/users/42 → '42'
Query stringAfter the ?, as key=value pairsreq.query.name/greet?name=Ada → 'Ada'
Request bodySent with POST/PUT, translated by body middlewarereq.body.titleJSON {"title":"Dune"} → 'Dune'

Two habits follow from the map. First, a query string can carry several pairs at once — ?sort=name&page=3 fills both req.query.sort and req.query.page — and any pair may be absent, so handlers that depend on one should supply a default, exactly as express-query.js falls back to 'stranger'. Second, all three sources deliver strings (the body is the exception: JSON can carry real numbers and booleans). Whenever a value must be a number — an id, a page, a count — converting it is your job.

Route patterns can do more

A route path is a pattern, not just a fixed string. You can use several parameters in one path (/users/:userId/books/:bookId), and a parameter matches exactly one path segment — /users/:id matches /users/42 but not /users/42/books. Express tries routes in the order you define them and uses the first match, so define specific routes before catch-all patterns.

One more routing fact worth knowing now: a route can have more than one handler. You can pass several functions to app.get() and they run in order, each handing off to the next — which is exactly the mechanism the next section is about.

Middleware: The Express Assembly Line

Middleware is a function that sits between the incoming request and the route handler that finally answers it. Every middleware function receives three arguments:

  • req — the request object: the URL, the method, the headers, and anything earlier middleware attached to it.
  • res — the response object: your way of sending the answer back.
  • next — a function you call to hand the request to the next function in line.

Picture an assembly line in a factory. The request is a product moving down the line on a conveyor belt. Each workstation does one small job — inspects the product, stamps it, wraps it — and then the belt carries it to the next station. The last station is your route handler, which finishes the product and ships it: it sends the response. Middleware is how Express apps are really built: instead of one giant handler doing everything, you line up small, single-job functions and the request flows through them in the order you registered them.

You register middleware with app.use(). A function passed to app.use() with no path runs for every request, whatever the URL. Order is everything: Express runs the line top to bottom, in the exact order your code calls app.use() and defines routes.

  1. The request arrives. A browser asks for GET /. Express starts at the top of your file and looks for the first function registered for this request. Nothing has run yet — no logging, no checking, no response.

  2. The logger runs. The first middleware writes a line to the console (in middleware-order.js that is “Middleware 1: request received”). Its job is done, but the request is not answered. Calling next() moves the request one station down the line.

  3. The checker runs. The second middleware inspects the request (“Middleware 2: checking the request”). A real checker might reject a request that lacks a required header — by sending an error response itself and not calling next(), which stops the line on purpose. This one is satisfied, so it calls next().

  4. The route handler answers. The last station matches GET /, logs its line, and calls res.send('Done'). Sending the response is what ends the request's journey — there is no next() after this because there is nothing left to hand off to.

The classic beginner bug: forgetting next()

If a middleware function neither sends a response nor calls next(), the request simply hangs. The browser spins, no error appears anywhere, and eventually the browser gives up. The server is not crashed — it is waiting forever at a station where nobody moved the belt. When a request hangs with no error message, check your middleware for a missing next() first.

The flip side is just as useful: a middleware that does send a response should not call next(). That is how gatekeeping works — a checker that finds a problem answers the request itself (often with an error status) and the route handler never runs at all. Section 2.6 and Week 4 both build on that idea. To be precise, the hang happens only when a middleware neither sends a response nor calls next(); a middleware that answers the request itself ends the line on purpose — Week 4's login guard does exactly that, replying 401 and never calling next().

You can also mount middleware on one branch of the line instead of the whole line. Give app.use() a path as its first argument — app.use('/api', fn) — and that station only sees requests whose path starts with /api. Everything else walks straight past it. That is how you will later protect just the API, or log just the admin area, without touching the rest of the app.

One more thing middleware can do: carry data down the line. Because every station receives the same req object, an early middleware can attach something to it — req.visitTime = Date.now(), say — and every later station and the route handler can read it. Middleware is not only a filter; it is also how a request accumulates context as it travels.

Built-In and Third-Party Middleware

You rarely write every station on the line yourself. Express ships with some middleware built in, and the npm registry offers third-party middleware — packages other developers wrote that you install and plug into your line with the same app.use() call. This section covers the three you will use constantly: one that serves files, two that translate request bodies, and one famous logger.

express.static: let Express serve your files

Most apps have files that never change per request: images, CSS, client-side JavaScript, plain text files. Writing a route for each one would be silly. express.static is built-in middleware that maps a folder on disk to the web: a request for /hello.txt returns the file public/hello.txt, and a request for / returns public/index.html if it exists. If no file matches, static politely calls next() and the request continues down your line.

$ curl http://localhost:3000/hello.txt Hello from the public folder! $ curl http://localhost:3000/ <h1>Static home page</h1> --- server console --- Listening on port 3000

Notice what is not in the console: no route handler ran. The static middleware answered both requests itself. That is the assembly line working as designed — a station that can finish the job does, and the request never travels further.

Order pitfall: static can shadow a route

Because the line runs in registration order, a static file wins over a later route with the same URL. If public/index.html exists, a request for / is answered by static middleware and your app.get('/', ...) handler below it never runs — no error, no warning, just the file. When a route mysteriously "does nothing," check whether an earlier station is answering its requests first.

Body translators: express.json() and express.urlencoded()

You met these in Week 1; here is their place on the line. A request body arrives as raw text. Two built-in middleware functions translate it into a JavaScript object on req.body:

  • express.json() translates bodies sent as JSON (JavaScript Object Notation — the text format for data you will meet properly in Section 2.4), which is how APIs receive data.
  • express.urlencoded() translates bodies sent by ordinary HTML forms, which encode fields as name=Ada&plan=free.

Both are ordinary middleware: they run early in the line, fill in req.body, and call next(), so by the time your route handler runs, the body is already a usable object. Forget to register the right one and req.body is empty — another silent, confusing failure with the same root cause as a missing next(): a station on the line was never installed.

morgan: a logger that writes your server's diary

morgan is a third-party middleware package (npm install morgan) that logs one line per request: the method, the path, the status code your server answered with, how long it took, and the size of the response. During development it is the fastest way to see what your server is actually being asked for. Its 'dev' format is the one used in most tutorials:

Where middleware comes from

The stations in this section come from three places, and it is worth keeping them straight:

These ship inside Express itself — no install step, just app.use(). This week you used three: express.static (serve files), express.json (read JSON bodies) and express.urlencoded (read form bodies). If a capability is built in, prefer it: it is maintained with Express and every Express developer recognizes it on sight.

These are npm packages written by other developers: npm install morgan, then require it and plug it into the line like any other middleware. The ecosystem is huge — logging, cookies, sessions, security headers, file uploads. Installing one is a real decision, though: you are trusting its maintainers with code that runs on every request, so pick packages that are widely used and actively maintained.

Any function with the (req, res, next) shape is middleware, including the ones you write. Yours are for jobs specific to your app: stamping a request with a time, checking a header, attaching data the handlers will need. Section 2.2's logger and checker were both hand-written middleware.

Whichever shelf a station came from, the rules from Section 2.2 apply unchanged: it runs in registration order, it sees the requests that reach it, and it must answer or call next().

RESTful APIs: Design, JSON and Status Codes

An API (application programming interface) is a way for one program to ask another program for data or actions, using agreed rules instead of a human clicking a page. A RESTful API is an API designed in the REST style, and REST itself rests on a few plain ideas you can hold in your head:

  • Everything is a resource — a thing your app keeps: a book, a user, an order. Each resource gets its own URL.
  • URLs are nouns, not verbs. The address names the thing (/api/books, /api/books/2), never the action. You will not see /getBook or /deleteBook in a REST API.
  • The HTTP method carries the verb. GET reads, POST creates, PUT replaces, DELETE removes. The method plus the noun says everything.
  • Data travels as JSON, and the status code says how it went — for successes and failures alike.

Why be this strict? Because a client programmer who has never seen your code can guess your API. If /api/books lists books, then /api/books/2 is book 2, POST /api/books creates one, and /api/users almost certainly lists users. That predictability is the whole point of the standard.

Methods are CRUD verbs

Most data work is four operations, nicknamed CRUD: Create, Read, Update, Delete. REST maps them onto HTTP methods like this:

POSTCreatePOST /api/booksAdd a new book from the JSON body201
PUTUpdatePUT /api/books/1Replace book 1 with the JSON body200

Look at the route column: only two URL shapes, /api/books and /api/books/:id, cover all five operations. The method — not the URL — says which operation. And notice how Week 2 comes together in that second shape: the :id route parameter from Section 2.1 is how the API knows which book you mean.

One close relative deserves a sentence: PATCH also updates, but where PUT replaces the whole record with what you send, PATCH changes only the fields you send and leaves the rest alone. This course uses PUT.

JSON: the language of APIs

JSON (JavaScript Object Notation) is a text format for structured data: objects with "key": value pairs, arrays in square brackets, strings in double quotes, numbers and true/false bare. It looks like a JavaScript object because it grew out of one, but it is plain text, so every language can read and write it. When your handler calls res.json(books), Express converts the JavaScript value to JSON text and labels it with the application/json content type. When a client sends JSON to you, express.json() — the translator from Section 2.3 — converts it back. JSON out, JSON in: that round trip is the heartbeat of every API you will build or consume.

The Front End: Single-Page Apps That Consume APIs

Everything so far lives on the server. Now cross to the other side: the program running in the visitor's browser. In Week 1 of Web Dev I terms, a traditional site works page by page — click a link, the server builds a whole new HTML page, the browser throws the old one away and paints the new one. A single-page application (SPA) works differently:

  • The browser loads one HTML page, once.
  • JavaScript running in that page re-renders — redraws — just the parts that change when you click, type or navigate. The page itself never reloads.
  • The data behind those redraws comes from an API: the JavaScript asks a server for JSON and renders it, exactly like the book API you built in Section 2.4.

A front-end framework is a library that organizes this style of building — React, Vue and Angular are the famous ones. They all share two ideas worth learning in plain words, whatever framework you meet later:

  • A component is a reusable piece of interface bundled with the code that renders it: a book card, a search box, a navigation bar. You build a page by assembling components, the way the server side assembles middleware.
  • State is the data the interface currently depends on — here, the list of books. The rule that makes SPAs manageable: the screen is a function of the state. Change the state, re-render, and the screen is correct again. You never poke at individual pixels; you update the data and let the rendering follow.
First, the bridge: promises, async and await

A promise is a placeholder for a value that arrives later: the operation has started, but the result is not in your hands yet. fetch() returns a promise, because a network request takes time your code cannot predict. Inside an async function — a function marked with the async keyword, which lets it pause mid-run — you can await that promise: your code stops at that line until the value lands, and if the request fails, the failure becomes an exception (an error thrown as a value your code can catch) that you can handle with try/catch. The .then() chain you are about to see is the same idea written differently: each .then() says “when the value arrives, run this next.”

The fetch() pattern

The browser's built-in way to call an API is fetch(): you give it a URL, it asks the server, and it hands you back the response so your code can read the JSON and render it. This is the pattern you will run against your own Week 2 server — the same rest-api.js from Section 2.4, with the front end and the API served from the same origin:

Read it as a pipeline. fetch('/api/books') sends GET /api/books to your server. The first .then runs when the response arrives and converts its body from JSON text into a JavaScript array with res.json(). The second .then receives that array — the exact JSON from Section 2.4 — and turns each book into an <li>. Adding a book is the same shape: fetch with method: 'POST' and a JSON body, then re-render from the updated state.

Two fetch() traps

First: fetch() only fails — its promise rejects (ends in failure instead of delivering a value) — on network problems, like no connection or a server that never answers. A 404 or 500 response still “succeeds” as far as fetch() is concerned, so check res.ok (a true/false property that is true exactly when the status is in the 2xx success family) before trusting the data — that is what the guard line in the sample does, turning a bad status into a thrown error. Second: a 204 response has no body at all, so never call .json() on it — there is nothing to parse and it throws. After a DELETE, just update the page from your state.

When the browser blocks your calls: CORS

If you open your front-end page from a file, or from a different port than your API, the browser will block its fetch() calls. That block is called CORS (cross-origin resource sharing): a browser security rule about which origins — an origin is a scheme, host and port together, like http://localhost:3000 — a page may read answers from. It is not a bug in your server; your server answered fine, and the browser refused to hand the answer to the page. This course's fix is to serve the page from the same Express app with express.static (Section 2.3), so page and API share one origin and CORS never comes up. The alternative, when the two genuinely live apart, is a cors middleware package on the server that tells browsers which origins are allowed.

Organizing an Express App: Routers and Error Handlers

This section is enrichment: it makes everything from this week easier to grow, and Week 3 and Week 4 assume you have seen it.

Your rest-api.js is one file with five routes, and it is already easy to lose track of. Now imagine the real app: books, users, orders, reviews — forty routes, three kinds of middleware, all in one file thousands of lines long. Nothing about it is wrong; it is simply unfindable. Every change means scrolling past unrelated code, and every teammate's edit collides with yours. The fix is not a new language feature. It is filing: group related routes into their own module, and mount each group at its own address.

The last two stations: the 404 handler and the error handler

A well-organized app also decides, deliberately, what happens when a request matches nothing, and what happens when a handler fails. Both are middleware — placed at the very end of the line, where only unanswered or failed requests ever reach them.

First, the 404 handler: a plain middleware registered after every route. Any request that reaches it was not answered by anything above, so its address names nothing your app has. For an API, it answers in JSON, like every other API response:

Second, the error-handling middleware. Ordinary stations have three arguments; an error handler has four — (err, req, res, next) — and that extra first argument is how Express recognizes it. It never runs during a normal request. It runs when an earlier handler calls next(err) with an error, or throws one: Express skips every remaining ordinary station and jumps straight here. Its job is to log the real problem on the server (where only you can see it) and send the client a calm, generic 500:

Expected output — this pattern is shown as the standard shape rather than a fresh capture: with this handler in place, a handler that fails produces one error logged on the server console and a 500 response whose JSON body is {"error":"Internal server error"}. (The API-level error you have already seen verified is the 404 JSON from Section 2.4: {"error":"Book not found"}.) The client never receives the stack trace — that stays in your server log, where it helps you and leaks nothing.

One modern convenience belongs here. In Express 5, if an async handler — a handler written as an async function, so it returns a promise (Section 2.5) — has that promise reject (the async version of throwing an error), Express forwards the error to the error-handling middleware automatically. try/catch is still needed for errors thrown later inside plain callbacks — functions you hand to other code, to be run whenever some work finishes, like a timer firing or a file read completing — which no framework can catch for you.

Express 5 details that do real work

This course teaches Express 5, the current version. Three of its details matter in this section:

  • Async errors are forwarded automatically (above): when an async handler's promise rejects, Express sends the error to the error-handling middleware on its own — no wrapper code needed.
  • Catch-all routes: a wildcard is a catch-all path pattern, and Express 5's router rejects a bare '*' path — app.get('*', ...) throws an error at startup. Write a catch-all as middleware with app.use, exactly as this section's 404 handler does, or use a named wildcard such as '/*splat' when you need a real route.
  • The body parsers are built into Express (express.json(), express.urlencoded()), so there is no separate parser package to install.

Put the week's architecture together and the line reads: global middleware (logger, body translators, static files) at the top, routers in the middle, then the 404 handler, then the error handler, last of all. Every request has a defined path through the app — including the requests that fail.

  1. The front end asks. The click handler sends fetch('/api/books', { method: 'POST', ... }) with the new book as a JSON body. The page does not reload; the request travels in the background (Section 2.5).

  2. The line processes it. On the server, morgan logs the request, then express.json() translates the JSON body into req.body and calls next(). Static middleware finds no matching file and passes it on (Sections 2.2 and 2.3).

  3. The router handles it. The request reaches the books router mounted at /api/books; its POST / handler reads req.body.title and req.body.author, assigns the next id, and stores the book (Sections 2.4 and 2.6).

  4. The API answers. The handler replies 201 Created with the new book — including its server-assigned id — as JSON. If the book had not existed or the data were bad, the same machinery would have produced the JSON 404 or a 400 instead.

  5. The screen follows. Back in the browser, the fetch() promise resolves, the code adds the returned book to its state, and render() redraws the list — now three books, exactly as in the Section 2.5 playground. One click used every idea in the week.
