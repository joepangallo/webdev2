Why Servers? Node and the JavaScript Runtime

Every page you built last term was a static page: the same file, sent to every visitor, exactly as it sits on disk. A photo gallery, a résumé, a restaurant menu that changes twice a year — static is perfect for those, and fast.

But think about what a static file cannot do. It cannot greet you by name, because it was written before you arrived. It cannot show your bank balance, your grades, or your shopping cart, because those are different for every visitor and they change while you watch. It cannot save anything you type into a form. For all of that, somebody has to run a program when your request arrives, work out what you should see, and build the answer on the spot. A page built fresh for each request is called dynamic.

Static: the vending machine

Everything inside was made earlier and sealed up. You pick an item, you get exactly that item, and so does everyone else. Nothing is cooked to order, and the machine learns nothing about you.

Dynamic: the short-order cook

You place an order, the cook reads it, checks what is in the fridge, and makes your meal. It takes a little longer, but the meal can be different for every customer — and the cook can write your order down for next time.

Example — the same request, two kinds of answer:

Static — the vending machine. Everyone asks for the same ready-made file: GET /about.html Response body: the saved about.html file — identical for Ada, for Grace, for everyone Dynamic — the short-order cook. The program reads each order before answering: GET /greeting?name=Ada Response body: Hello, Ada! GET /greeting?name=Grace Response body: Hello, Grace!

Client and server, in plain words

A client is the program that asks for something. On the web, that is usually your browser. A server is a program that waits for requests, does work, and sends back a response — the answer to one request. The word "server" also gets used for the computer the program runs on, which causes endless confusion. In this course, when we say "your server," we almost always mean your program.

The conversation is always the same shape: the client sends a request (a message that says what it wants, like "GET /about"), and the server sends back one response (the page, some data, or an error). The client always speaks first. A server sitting alone in a room says nothing until somebody asks.

Example — one raw request and its response:

Request (the client speaks first): GET /about HTTP/1.1 Host: localhost:3000 Response (the server's one answer): HTTP/1.1 200 OK Content-Type: text/plain About page
Why does the work move to the server at all?

Three reasons. Fresh data: the server can read the current state of a database instead of a file frozen last month. Secrets: code on the server can hold passwords and keys that visitors must never see — anything you send to a browser is public. Trust: you control the server, but you do not control the visitor's browser, so prices, grades and permissions are always checked on the server, never only in the page.

What is a runtime?

JavaScript code cannot run by itself. Something has to read it, carry out its instructions, and give it ways to interact with the world. That something is a runtime: the environment a program runs inside, including the engine that executes the code plus the tools the code is allowed to use.

Your browser is one runtime. Inside it, JavaScript can change the page, react to clicks and ask for data over the network — but it is deliberately fenced in. Browser JavaScript cannot read files off your hard drive, open its own network connections to anywhere it likes, or keep running after you close the tab. Those fences protect you from hostile websites.

Node (often called Node.js) is a second runtime for the same language, built for the other side of the fence. Node takes the V8 engine — the exact JavaScript engine inside Chrome — and surrounds it with tools a browser would never allow:

ToolIn the browserIn NodeWhy it matters for a server
The V8 engineYesYes — the same engineYour JavaScript skills carry over unchanged
Reading and writing filesNoYes — the fs moduleServers save uploads, logs and data in files
Listening for network connectionsNoYes — the http moduleThis is being a server: waiting for requests
The page (document, window)YesNo — there is no pageNode code never touches HTML directly; it sends it
Environment and system infoAlmost noneYes — processServers read settings like port numbers from the system

So "server-side logic with a JavaScript runtime" — the wording of Objective 2 for this course — simply means: your JavaScript, running in Node, on the server, deciding what each response should be. Same language as the browser, different toolbox, different job.

One worker, a waiting line, and non-blocking work

Node runs your code on a single thread. A thread is one sequence of instructions being carried out — picture a single worker who can only do one thing at a time. That sounds like a terrible design for a server with a thousand visitors, until you notice what a server actually spends its time doing: waiting. Waiting for the database to answer, waiting for a file to load, waiting for the network. The work itself — deciding what to send — is usually quick.

Node's answer is non-blocking input/output, usually shortened to non-blocking I/O. Input/output (I/O) means any operation that talks to something outside your code: a disk, a database, the network. When your code starts an I/O operation, Node does not sit and stare at it. It hands the waiting to the system, puts a note on a list — "when this finishes, run this little function," called a callback — and the worker moves on to the next request. When the I/O finishes, the callback joins a waiting line called the event queue, and the event loop — the worker's endless routine of "check the line, run the next job, check again" — picks it up.

Think of a coffee shop with one barista. A blocking barista would pour a slow drip coffee and stand watching it drip while the line grows. A non-blocking barista starts the drip, takes the next three orders, and hands the coffee over when it is ready. One worker, many customers, no standing around. The catch: if one order itself takes the barista five full minutes of continuous work — a huge calculation, say — everyone waits, because the worker truly is busy. Node is excellent at waiting-heavy work (which is most web work) and poor at long, continuous calculations.

The one rule that follows from this

Never make the worker stand and watch. Node's file tools come in pairs like readFile (non-blocking: starts the read, runs your callback later) and readFileSync (blocking: the worker waits). Later in this course you will use the Sync versions, because they keep a short example easy to follow, and they are fine in tiny scripts and startup code. In a request handler, they stall every other visitor.

Two halves of every web app

You will hear the two sides called the front end and the back end. The front end is everything that runs in the visitor's browser: the HTML, CSS and browser JavaScript from Web Dev I. The back end is everything that runs on the server: your Node program, its routes, and the data it guards. This course is mostly about the back end — but notice that the boundary between them is exactly the request/response conversation. The front end asks; the back end answers.

Follow one request on its whole journey

Step through what happens when a visitor asks your server for a page that needs fresh data:

1 · BrowserThe visitor clicks a link or submits a form.
→
2 · Request travelsAn HTTP request crosses the network to your server's address and port.
→
3 · Your code runsNode wakes up the function that handles this route.
→
4 · Data is fetchedYour code asks the database or a file — without blocking other visitors.
→
5 · Response returnsYour code builds the answer and sends it back. The browser displays it.

  1. The browser asks. Every journey starts with a client. The browser builds an HTTP request: a method (GET here), a path (/grades, say), and headers — small labeled facts about the request, like which browser this is.

  2. The request finds your program. It arrives at a computer, at a numbered port — the door a specific program listens behind. Your Node server is listening on that port, doing nothing but waiting. Waiting is cheap; an idle server uses almost no processing power.

  3. Your code decides what this request is. Which path? Which method? Is the visitor logged in? The part of your code that answers one kind of request is called a route handler. Choosing the handler is called routing, and it is the subject of most of this week.

  4. Fresh data, gathered without blocking. The handler needs this visitor's grades, so it asks the database. That question takes time — and thanks to non-blocking I/O, the worker serves other visitors while the database thinks. When the answer arrives, the handler's callback runs.

  5. The response goes home. Your code packages the answer: a status code (200 means "OK"), headers, and the body — the actual content. The browser receives it and shows the page. One request, one response, done. The server goes back to waiting.

Your First Node Program and the http Module

Time to run JavaScript with no browser anywhere in sight. A Node program is just a text file of JavaScript. You run it from a terminal — the text-only window where you type commands to your computer — with the command node followed by the file name. And in the server's own terminal there is just the one listening line: the server prints nothing per request unless you tell it to.

One sharp edge: req.url includes the query string

req.url is the path plus any query string — the extra data after a ? in an address, like ?lang=en. So a request for /about?lang=en does not equal '/about', and this hand-written chain would send it to the final else branch: "Page not found", even though the visitor asked for a page that exists. The curl examples above carry no query strings, which is why they match cleanly. Real programs handle this in one of two ways: they pull the address apart with the built-in URL class and compare only the path, or they let Express do the matching — Express compares the path and sets the query string aside for you. That is one more reason Express exists.

Ports: the numbered doors

One computer runs many programs that use the network, so an address alone is not enough — the request also names a port, a number from 0 to 65535 that identifies which listening program should receive it. You met ports in Web Dev I with addresses like localhost:5500. Three ports matter this week:

npm: Packages and package.json

Your server so far uses only tools that ship inside Node. But nobody writes everything from scratch. If you need your server to talk to a database, check a password, or — as in the very next section — handle routes without hand-written plumbing for every page, you use code somebody else wrote, tested and published. A reusable bundle of code like that is called a package. (You will also hear module: in Node, a module is any file of code you can load with require or import. A package is a folder of one or more modules, bundled up for sharing, usually with a name and a version number.)

The tool that downloads, installs and keeps track of packages is npm, the Node Package Manager. It installs automatically alongside Node. Behind it sits the npm registry, a giant public library of packages — over two million of them — that your computer downloads from when you ask.

Every Node project keeps its identity card in one file: package.json. It records the project's name, its starting file, handy command shortcuts, and — most importantly — exactly which packages the project depends on. Installing a package: npm install

One command does three jobs at once:

  • It downloads the package (and every package that package needs) from the registry into a new folder in your project called node_modules. Express lands at node_modules/express, and your code loads it with require('express') — no path needed, Node knows to look in node_modules.
  • It records the dependency in package.json, under "dependencies". A dependency is a package your program needs in order to run.
  • It writes package-lock.json, a precise receipt listing the exact version of every downloaded package, so the same project installs identically on another machine.
Never share or commit node_modules

The node_modules folder can hold tens of thousands of files and is completely rebuildable: anyone with your package.json can recreate it by running plain npm install with no package name. That is the whole point of recording dependencies — the file travels, the folder does not. It is also why "it worked on my machine" so often means "my node_modules had something my package.json forgot to mention."

Dependencies vs devDependencies

Not every package is needed to run your program. Some are only needed while you develop it: test runners, code formatters, the auto-restart tool you will meet in Section 1.6. Those go in a separate list:

Version numbers: semantic versioning

Every package version is three numbers — 5.3.0 — following semantic versioning ("semver"), a promise about what changed:

PositionExample changeThe promise
MAJOR · 5.3.05.3.0 → 6.0.0Breaking changes. Your code might need edits to keep working.
MINOR · 5.3.05.3.0 → 5.4.0New features, added without breaking existing code.
PATCH · 5.3.05.3.0 → 5.3.1Bug fixes only. Safe to accept automatically.

That is why package.json records "express": "^5.3.0" with a caret (^). The caret means "5.3.0 or anything newer that keeps the same major number" — so the range allows 5.4.2, but never 6.0.0. Fixes and features can come in; breaking changes never sneak in. An exact "5.3.0" with no symbol means that version and no other; a tilde (~5.3.0) allows only patch updates.

The range is not the whole story, though. Once a package-lock.json exists, plain npm install keeps installing the exact version recorded in it, on every machine. The caret only gets a say when there is no lock file yet, or when you ask for newer versions on purpose by running npm update.

Example — what each range accepts and rejects:

Range in package.jsonAcceptsRejectsWhy
^5.1.05.4.26.0.0Same major number: new features and fixes may arrive, but a breaking new major never sneaks in

The three artifacts, side by side

After your first install, your project folder holds three things students constantly confuse. Keep them straight:

What it is: the identity card you own and edit. Name, version, entry point, scripts, and the dependency lists.

Who writes it: you — by hand, or by running npm init and npm install, which update it for you.

Share it? Always. It is the recipe every teammate and every deployment starts from.

What it is: the exact receipt. Not just "Express 5.x" but the precise version of Express and of every package Express itself needed, with checksums.

Who writes it: npm, automatically, on every install. You never edit it by hand.

Share it? Yes — it is what makes "works on my machine" become "works on every machine, identically."

What it is: the downloaded code itself — a folder that can grow to tens of thousands of files.

Who writes it: npm, by unpacking what the registry sent.

Share it? Never. It is fully rebuildable from the other two files with one npm install.

Express: Your First App and Routes

Recall the raw http server: an if / else chain, a writeHead and an end for every single path, and no help at all with forms, JSON, or errors. Every real project outgrows it within a day. Express is a package — the one you installed in the last section — that sits on top of Node's http module and does that plumbing for you. It is the most widely used server framework for Node: a framework is a library that provides the skeleton of an application, so you fill in the parts that make your app yours.

The mental model to keep

An Express app is a list of routes, checked from top to bottom. A request arrives, Express walks the list asking "method and path — match?" and the first matching handler runs and sends the response. No match at all? Express sends its built-in 404. When you add a route, you are adding one line to that list — order matters, which becomes important in Week 2.

Notice what did not change from the raw server: req and res are still the request and response objects, a handler still runs once per request, and listen still takes a port. Express is not a different world — it is the same world with the repetitive parts removed. That is why this course taught you the raw version first: now you know what Express is doing for you, and when something goes wrong you will know where to look.

Handling GET and POST Requests

So far your server only answers GET requests. GET is one of HTTP's methods — verbs that say what the client is trying to do. Two of them run almost everything you will build this term:

GET — "give me something"

The client is asking to read. Loading a page, viewing a profile, running a search: all GET. A GET request carries no body; everything it sends travels in the address itself. GET should never change anything on the server — refreshing a GET page is always safe.

POST — "here is something new"

The client is sending data for the server to act on: signing up, logging in, posting a comment. That data travels in the request body — a separate part of the message after the headers, like the letter inside an envelope rather than the address written on it.

Example — the two verbs as raw requests:

GET /books HTTP/1.1 Host: localhost:3000 POST /books HTTP/1.1 Host: localhost:3000 Content-Type: application/x-www-form-urlencoded title=Dune&author=Frank+Herbert

Same path, different verb, different luggage. The GET is just a request line and headers — there is nowhere else for data to ride. The POST adds a Content-Type header announcing the body's format, a blank line, and then the body itself: one book, packed as name=value pairs.

GET data: the query string

If GET has no body, how does a search page send your words to the server? In the address. A query string is the part of a URL after a ?: a list of name=value pairs joined by &, like this:

http://localhost:3000/search?q=express+tips&page=2

That address asks for the path /search and carries two pieces of data: q is express tips (in a URL, a space is written +) and page is 2. Query strings are visible to anyone who can see the address — in the browser bar, in history, in logs — which is exactly why passwords and other secrets must never travel in one. Use GET and query strings for reading and searching; use POST for anything private or anything that changes data.

Example — a search address becomes an object on the server:

Address: /search?term=vue&page=2 What Express hands your handler as req.query: { term: 'vue', page: '2' }

Notice the quotes on the '2'. Everything in an address is text, so page arrives as the string '2', not the number 2 — if your code needs to do arithmetic with it, converting it is your job.

POST data: forms pack, the server unpacks

Quick recap from Web Dev I, because everything here hangs on it. When a visitor submits an HTML form, the browser packs each form control into a name=value pair — and the name attribute is the label on each package. A control with no name is left out entirely, no matter what the visitor typed. With method="post", those pairs are joined with & and placed in the request body: name=Ada&plan=free.

But there is a catch. The body arrives at your server as raw text. Express does not automatically know how to turn name=Ada&plan=free into something your code can use — and a different kind of client, like a phone app or another program, might send the same data as JSON instead: {"name":"Ada","plan":"pro"}. JSON (JavaScript Object Notation) is a text format for structured data that looks like a JavaScript object; it is how programs talk to each other all over the web.

So Express gives you two translators, switched on with app.use — Express's way of adding a processing step that runs for requests before they reach your routes (you will take this apart properly in Week 2, under its real name: middleware):

  • express.urlencoded({ extended: true }) — reads bodies sent by HTML forms and turns the pairs into an object.
  • express.json() — reads bodies sent as JSON and turns them into an object.

How does each translator know which bodies are its job? It reads the request's Content-Type header — the label a client attaches to say what format its body is in — and leaves every other body alone. $ curl -X POST http://localhost:3000/signup -d "name=Ada&plan=free" {"received":{"name":"Ada","plan":"free"}} $ curl -X POST http://localhost:3000/signup -H "Content-Type: application/json" -d '{"name":"Ada","plan":"pro"}' {"received":{"name":"Ada","plan":"pro"}} --- server console --- Listening on port 3000

Three curl flags do the work in those commands. -X POST sets the method. -d supplies the body — and, used alone, it also labels that body as form data (Content-Type: application/x-www-form-urlencoded), just as a browser form does. -H adds a header of your choosing, and the second command uses it to relabel its body as JSON. That label is the only reason the JSON example works: leave out the -H and the form translator claims the body, misreads the whole JSON text as one oddly named field, and the JSON translator never looks at it.

Two different body formats went in; the same shape of answer came out, because req.body held { name: 'Ada', plan: 'free' } the first time and { name: 'Ada', plan: 'pro' } the second. Forget both translators and req.body is undefined: nothing translated the body, so there is no object at all, and the first line that reads a field from it — req.body.name, say — fails with TypeError: Cannot read properties of undefined. That is the single most common beginner bug with POST, and now you know its cause before you ever meet it.

Example — one book, from body text to req.body:

Body as it arrives (form encoding, exactly as the raw POST above sent it): title=Dune&author=Frank+Herbert req.body after express.urlencoded has translated it: { title: 'Dune', author: 'Frank Herbert' }

The + in the body is an encoded space — the same encoding you met in query strings — so Frank+Herbert reaches your code as Frank Herbert. The pairs split on &, each name becomes a property, and your handler reads req.body.title and req.body.author without ever touching the raw text.

express.urlencoded() is middleware; s2-3 explains where it comes from. Without it, req.body is undefined in Express 5.

req.body is untrusted mail

Everything in req.body was typed, or crafted, by whoever sent the request — including people who never saw your form and are sending requests with curl. Never assume a field exists, is the right type, or is honest. Checking what arrived before you use it is called validation, and Week 3 gives it a full section.

See exactly what a form sends

This playground runs in your browser, and its preview does something special with forms: when you press the submit button, it intercepts the submission and shows you precisely what the browser would send — the method, the address, and the body as a table of names and values. Press Sign up and read the report. The body is name=Ada&plan=free, and a warning says one field was not sent: the coupon code, because its control has no name.

Your task: get the coupon code to the server. Give the coupon input the attribute name="coupon", then press Sign up again. The warning disappears, and the body grows to name=Ada&plan=free&coupon=SAVE10.

Connect the dots: before your fix, the body in that report — name=Ada&plan=free — was character-for-character the body in the first curl command above, the one that produced the first verified output. After your fix it carries a third pair, coupon=SAVE10, and the server in express-post.js would find a third property, coupon, in req.body. A browser form and curl are just two different clients packing the same envelope.

Debugging and Error Handling

Your server will break. Not because you are careless — because every server breaks, including those written by people with twenty years of experience. The skill that separates beginners from developers is not avoiding errors; it is reading them. This section is enrichment — it goes beyond the minimum for Objective 2 — and it will save you more hours this term than any other.

Rule one: read the error message first

When Node code fails, it prints an error message followed by a stack trace: the list of function calls that were in progress when things went wrong, most recent first. Beginners scroll past this wall of text to the reassuring prompt at the bottom. Do the opposite. Read it in this order:

  1. The first line is the headline. It names the kind of error and what went wrong: TypeError: Cannot read properties of undefined, or Error: listen EADDRINUSE. Half the time, the headline alone tells you the fix.
  2. Find the first line that names YOUR file. The stack trace mixes your code with Node's and Express's internals. Scan down until you see one of your file names — at Object.<anonymous> (/home/you/server.js:7:15) — that file name, line number (7) and column (15) are where your code was when it failed.
  3. Ignore the rest, for now. The frames below yours are the machinery that called your code. They matter for library authors. For you, headline + your line is almost always enough.

Example — a real stack trace, read the section's way:

Real output — captured by running this exact program (Node 26).

account.js:2 console.log(account.balance); ^ TypeError: Cannot read properties of undefined (reading 'balance') at Object.<anonymous> (account.js:2:21) at Module._compile (node:internal/modules/cjs/loader:…) … (more of Node's own frames — the part you can ignore for now)

Now annotate it. Node first re-prints the line that failed — line 2, the console.log — with a caret under the exact spot. The headline says what went wrong: the code tried to read balance off a value that is undefined, because account was never given a real object. And the first frame naming your file, account.js:2:21, confirms the place: line 2, column 21. Headline plus your frame was enough to find and understand this bug; the frames below belong to Node's module machinery.

Rule two: console.log is a flashlight

When the error message is not enough, make the program tell you what it is doing. Sprinkle console.log lines at the points you are unsure about — the value of req.url when a request arrives, the contents of req.body inside a POST handler — run it, trigger the problem, and read what prints in the server's terminal. Then remove the logs you no longer need; a server that narrates every request forever buries real errors in noise. Professional loggers exist, and Week 2 mentions one, but the flashlight comes first.

That one line settles the Section 1.5 mystery in seconds. If the terminal shows Body received: undefined, no translator handled the body: check your app.use lines and the Content-Type the client sent. If it shows Body received: {}, a translator ran but no named fields arrived: check the name attributes in the form. If it shows your data, the bug is somewhere after this line.

Rule three: one change at a time

Reading and logging tell you where to look. What turns them into a fix is a routine: the same few steps, in the same order, every time — instead of editing whatever looks suspicious.

  1. Read the error. The headline first, then the first stack frame that names your own file. That is rule one.
  2. Make it fail again, on purpose. Before you touch any code, repeat exactly what you did — the same curl command, the same click — and check that the same error comes back. Now you have a test you can run as often as you like. If you cannot make a bug appear on demand, you can never be sure you made it go away.
  3. Shine the flashlight. Add console.log near the line the trace named, run your test, and compare what the values are with what you assumed they were. That is rule two.
  4. Change exactly one thing. Use what the logs showed you to make one guess, and make one edit.
  5. Run the same test again. If the error is gone, you know which edit fixed it. If it is still there, undo the edit and try your next guess.

Two cautions. Every edit, a log line as much as a fix, only takes effect once you restart the server. And the fourth step is the one beginners skip: change three things at once and, when the error vanishes, you cannot tell which change mattered — or whether one of the other two planted a new bug.

Example — the flashlight off, then on:

Without the log line, a visitor submits the signup form and the server terminal shows: (nothing new — a running server prints nothing per request unless you tell it to) After adding console.log('Body received:', req.body) to the handler, the same submission shows: Body received: { name: 'Ada', plan: 'free' }

Same request, same handler — the only difference is that now the program reports what it actually received, and a guess ("is the form even sending anything?") becomes a fact you can act on.

Three classic beginner errors

You will meet all three of these. Recognizing them on sight turns a half-hour panic into a ten-second fix. Open each one:

Error: listen EADDRINUSE: address already in use :::3000

What it means: your new server tried to listen on port 3000, but something already is — almost always your own server from a minute ago, still running in another terminal window, or this one, because you started it twice. EADDRINUSE is the system's way of saying "that address is taken."

How it looks depends on which server you started. With the raw http server from Section 1.2 — which has no error handling — you see the EADDRINUSE error printed, with a stack trace. With Express 5, the same failure arrives silently: Express hands the failure to the app.listen callback as its first argument, and the demos in this course ignore that argument. So a second copy of an Express demo prints Server listening on http://localhost:3000 and then quietly exits — it looks like it started and then "just stopped".

That pattern checks err first: if starting failed, it prints the real error and exits on purpose, instead of printing a success message for a server that never started.

The fix: find the old server and stop it (click its terminal, press Ctrl+C). Do not "fix" it by randomly changing ports — you will end up with three servers running three different versions of your code, answering on three ports, and no idea which one the browser is talking to. One server, one port, stopped and started deliberately.

Cannot GET / in the browser

What it means: this is Express's built-in 404 page. The server is running fine and received your request — but no route matches a GET for the path /. Notice it names the method as well as the path: Cannot POST /signup would mean the path exists in your mind but no POST route matches it.

The fix: compare the message with your route registrations, character by character. Did you register app.get('/home', …) instead of '/'? Did you register the route after starting a different copy of the server? Is the browser's address exactly the path you think it is? The message is never wrong about what it looked for.

Error: Cannot find module './sever'

What it means: your code asked Node to load a file or package that is not there. In this example the file is named server.js but the code says sever — a one-letter typo. The same message appears when you require('express') in a project where you never ran npm install: the module genuinely is not there to find.

The fix: read the name in the message and compare it, letter by letter, with the real file name or package name. If the name is right, check the location: are you running the command from the project folder, and does node_modules exist? Nine times out of ten it is spelling; the tenth time it is a forgotten install.

Catching errors on purpose: try / catch

Some failures you can predict. Code that calls a method on a value that turned out to be undefined, uses JSON.parse to turn text a visitor typed into an object, or reads a file that might not exist will fail sometimes. JavaScript's answer is try / catch: put risky code in a try block; if anything inside it throws an error (raises it, deliberately or by accident), execution jumps straight to the catch block, which receives the error as a value — its message property is the headline text — and the program carries on.

What happens when nothing catches the error depends on where it was thrown, and the three cases are worth telling apart. In the raw http server from Section 1.2, a throw inside the request handler crashes the whole Node process, taking every other visitor down with it. In an Express route handler, Express catches the throw for you: the stack trace prints in your terminal, that one client gets a 500 Internal Server Error response, and the server keeps running. But an error thrown later — inside a timer or another callback that runs after your handler has returned — is beyond Express's reach, and it crashes the process just as it would in the raw server. Week 2 shows how to decide for yourself what a 500 response says.

Read the console in this playground before you change anything. greet('') throws, and safeGreet does nothing to stop it, so the error escapes all the way out to the try / catch near the bottom. The line that starts with Escaped: is that outer catch speaking. It saves the script, but every caller of safeGreet would need the same safety net.

Your task: move the protection inside. Rewrite safeGreet so that it wraps its call to greet in its own try / catch and, when an error is thrown, returns 'Caught: ' followed by the error's message. You will know it worked when the console's second line changes to Caught: A name is required and every check is green.

One more experiment, once every check is green. Add the line console.log(greet('')); just above the last line and watch the console. Nothing catches that throw, so the script stops on the spot: an error appears, and The program kept running. never prints. That is an uncaught error in miniature. Delete the line again and the script recovers.

Stop restarting your server by hand

Every edit to a running server requires a stop and a restart, because Node loaded your file once, at startup. Node can take over that chore. Start the server with node --watch server.js instead of node server.js, and Node restarts it for you every time you save the file — watch mode is built in, so there is nothing to install. The edit–restart–retest loop shrinks to just edit–retest. The nodemon package from Section 1.3's devDependencies table does the same job, and you will see it in many tutorials written before Node could do this itself. Either way, it is a development convenience only — production servers do not change under their own feet.

Five mix-ups this week was designed to prevent

The mix-upThe correction
"The server is the computer in the corner."Sometimes — but in your code, "the server" is a program: the one listening on a port and running your handlers. The computer is just where it lives.
"Node is a language."Node is a runtime. The language is JavaScript, identical in the browser — what changes is the toolbox around it.
"A 404 means the server is down."A 404 means the server is up, answered politely, and had nothing at that path. A down server gives you no status code at all — the connection itself fails.
"The form sent it, so req.body must have it."Only if the control had a name and the matching translator (express.urlencoded or express.json) was switched on. Two separate places to check.
"It worked yesterday, I changed nothing."Something changed — an edit saved after the server started (it is still running the old file), a second server on another port, a deleted node_modules. Section 1.6's routine exists to find which.
