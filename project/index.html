The Final Project: Your Full-Stack App

You design and build one complete web application — server, API, database and logins — and it grows by one milestone after each week of the course. Nothing is thrown away: the small server you write in Week 1 is the same app you finish in Week 4, with accounts and roles switched on.

How the project works

Each milestone uses only what the class has covered up to that week, and each one is checked before the next begins. If you keep up weekly, the "final project" is never a last-minute mountain — it is four small climbs.

One app

Pick a theme below. Every milestone adds to the same codebase, so your early decisions — names, folders, data shapes — keep paying off.

A milestone per week

Server after Week 1, API and front end after Week 2, real persistence after Week 3, accounts and roles after Week 4.

It has to run

Your app must start with one command and answer requests on your machine. "It worked in a screenshot" is not a deliverable.

Show your work

A short README explains what your app does and how to run it. Future you — and your instructor — will thank present you.

Start embarrassingly small.

The best Week 1 server stores nothing, styles nothing, and answers two routes. You will grow it every week. A tiny app that runs beats a grand design that does not.

Choose your theme

Your app needs data worth storing: a collection of things that can be listed, added, edited and deleted, where some actions are public and some are private. These themes all fit. Pick one, adapt one, or propose your own in the same shape.

Track a personal collection — books, games, vinyl, trading cards. Data: items with a title, a category, a year and a note. Public: browse the collection. Private: only the owner adds or edits items.

Run a club or team: members, events and sign-ups. Data: members, events, attendance. Public: see upcoming events. Private: members sign up; officers manage the roster.

Book a shared resource — tutoring slots, lab seats, studio time. Data: time slots and who holds them. Public: see open slots. Private: signed-in users book and cancel their own slots.

A shared recipe collection with ingredients and steps. Data: recipes with ingredients, time and difficulty. Public: search and read recipes. Private: cooks contribute and edit their own.

A small business — a food truck, a repair shop, a salon — with a menu or service list and a request form. Data: offerings and customer requests. Public: browse offerings, send a request. Private: the owner views and answers requests.

Example — one theme, worked:

Take the Collection tracker, tracking a shelf of books. The one main collection is books: each book has a title, a category, a year and a note. Browsing is public; adding, editing and deleting belong to the owner (that last part switches on at Milestone 4). Its routes:

VerbURLPurpose
GET/api/booksList every book in the collection (public)
GET/api/books/:idShow one book (public)
POST/api/booksAdd a book (owner only)
PUT/api/books/:idEdit a book (owner only)
DELETE/api/books/:idRemove a book (owner only)

Whichever theme you choose, write down — before any code — the one main collection your app stores (books, events, slots, recipes, requests). Every milestone revolves around it.

Milestone 1 · A Running Server

Goal: a Node project with an Express server that starts cleanly and answers real routes. This is the skeleton everything else hangs on.

Builds on: Week 1 — Node, the http module, npm, Express, GET and POST.

RequirementWhat "done" looks like
Project setupnpm init done; express in dependencies; a start script in package.json
Servernode starts it with no errors; it listens on a port taken from process.env.PORT with a sensible default
RoutesAt least three GET routes (home plus two about your theme) and one POST route that reads a form or JSON body and answers with what it received
Not foundAn unknown address gets a clear "not found" response, not a crash or a hang

Done looks like:

What comes back:

HTTP/1.1 200 OK Content-Type: application/json { "title": "Dune", "category": "Sci-fi", "year": 1965 }

Reference starter blueprint (adapt the routes to your own theme):

Reads process.env.PORT with a fallback to 3000, turns on JSON and form body parsers, answers three GET routes plus one POST route, and includes a clean 404 fallback.

Declares express under dependencies and a start script so npm start launches your server with one command.

Every Milestone 1 requirement is visible in those two files: process.env.PORT || 3000 lets hosting platforms choose the port while keeping 3000 locally, express.json() and express.urlencoded() make POST /api/books work for both curl JSON requests and HTML forms, and the final app.use(...) prevents hangs or ugly defaults on unknown paths.

Deliverable: your project folder (or repo link) plus a one-paragraph note naming your theme and your main collection.

Milestone 2 · API and Front End

Goal: your main collection becomes a small REST API, and a web page uses it. For now the data can live in memory — Week 3 makes it permanent.

Builds on: Week 2 — routing in depth, middleware, REST design, single-page front ends.

RequirementWhat "done" looks like
REST endpointsGET all, GET one by id, POST, PUT, DELETE for your main collection, with nouns-not-verbs paths like /api/books
Status codes201 on create, 204 on delete, 404 with a JSON error when an id does not exist
MiddlewareJSON body parsing, a request logger, static file serving, and an error-handling middleware — in an order you can explain
Front endOne page built with a front-end framework (for example Vue loaded from a CDN script tag — no build step needed, as in Week 2) that fetches your API, renders the list from the framework's state, and has a form that adds a new item through the API (no page reload)
OrganizationRoutes for the collection live in their own router file, mounted with app.use

Done looks like:

What comes back:

HTTP/1.1 201 Created Content-Type: application/json { "id": 3, "title": "The Left Hand of Darkness", "category": "Sci-fi", "year": 1969, "note": "First edition" }

Reference starter blueprint (router + styled Vue SPA served by express.static('public')):

Moves all five CRUD routes into their own module, mounted with app.use('/api/books', booksRouter) in server.js.

Uses Vue 3 from a pinned CDN script (no build step): @submit.prevent stops page reloads and calls addBook(), which POSTs JSON and pushes the server's 201 response into reactive state.

Clean responsive CSS for the SPA list, form row, delete buttons, and error banner — served automatically at /styles.css.

Notice how @submit.prevent in Vue replaces event.preventDefault(), letting the form work cleanly with the Enter key while sending JSON via fetch() and updating the screen with zero full-page reload.

Deliverable: the updated project, plus a short list of your endpoints (method + path + what it does).

M3After Week 325 points

Milestone 3 · Real Persistence

Goal: restart your server and your data is still there. Your API now reads and writes a real database — MongoDB or MySQL, your choice — and refuses bad data.

Builds on: Week 3 — cookies and sessions, relational vs non-relational databases, CRUD, validation and configuration.

RequirementWhat "done" looks like
DatabaseMain collection stored in MongoDB or MySQL; all five API operations use the database, not an in-memory array
Safe queriesMySQL: every query uses placeholders — no user input glued into SQL strings. MongoDB: filters built from validated fields only
ValidationThe server rejects creates/updates with missing or wrong-typed required fields, answering 400 with a useful JSON error
ConfigurationConnection string and port come from environment variables (a .env file locally); no secrets anywhere in the code or the repo
Seed dataA documented way to load a few starter records, so a fresh clone is not an empty app

MongoDB generates the _id when the record is saved — yours will differ. Restart the server and this record is still there; that is the milestone.

A note on ids: the milestone checks keep illustrating the API with the simple numeric ids from the in-memory stage (Milestone 2). In the MongoDB version, the document's _id — that 24-character ObjectId — is what plays the id role in the URL.

Reference starter blueprint (seed script + environment template):

Run once with node --env-file=.env seed.js so a fresh clone starts with visible starter records instead of an empty list.

Commit .env.example with placeholder text and keep your real .env in .gitignore.

Notice the idempotent guard if ((await books.countDocuments()) === 0) in seed.js: running the seed command twice by accident will never duplicate your starter records.

Deliverable: the updated project; your README now includes setup steps that end with a running app and visible seed data.

M4After Week 430 points

Milestone 4 · Accounts and Roles

Goal: your app knows who is using it and what they may do. This is the finished full-stack application — the course in one project.

Builds on: Week 4 — authentication, sessions, hashing, roles and protected routes, security hygiene.

RequirementWhat "done" looks like
AccountsRegister and log in; passwords stored only as salted hashes (never plain text, never reversible); a new account's role is set by the server, never read from the sign-up form
SessionsLogin creates a session; the browser carries only the session ID cookie; logout truly ends it
AuthorizationAt least two roles (for example member and admin, or owner and visitor) with different powers, enforced on the server
Protected routesCreating/editing/deleting through the API requires the right login and role: 401 when signed out, 403 when signed in but not allowed
Hygiene passSecrets in environment variables, cookie flags set sensibly (httpOnly, sameSite, a lifetime), dependencies checked, no passwords or keys in the repo

Done looks like:

Ask to edit a book with no login cookie, and the server refuses before anything is touched:

HTTP/1.1 401 Unauthorized Content-Type: application/json { "error": "Please log in" }

The same request with the session cookie from logging in as the book's owner (your session id will differ):

HTTP/1.1 200 OK Content-Type: application/json { "id": 3, "title": "The Left Hand of Darkness", "category": "Sci-fi", "year": 1969, "note": "First edition, good condition" }

Signed in is not always enough. The same request carrying a different user's session cookie — someone signed in, but not the book's owner — is refused as well, and the stored book is left unchanged:

HTTP/1.1 403 Forbidden Content-Type: application/json { "error": "Only the owner can edit this book" }

Reference starter blueprint (guards + HTML/CSS login & register page):

Two small reusable middleware functions enforcing authentication (401) first, then role authorization (403).

Two separate POST forms — notice neither form includes a role input, because the server always assigns the default role at registration.

Two-column responsive layout that stacks cleanly on phones, with clear focus outlines and full-width buttons.

Pair middleware/auth.js with an ownership check inside your PUT and DELETE handlers (book.ownerId !== req.session.userId && req.session.role !== 'admin' → 403) to satisfy every Milestone 4 requirement end to end.

Deliverable: the finished project, a README with setup and test accounts (a demo member and a demo admin — give the admin its role in your seed data, not through sign-up), and a half-page reflection: what your app does, and which course idea was hardest to make real.

How the project is graded

One hundred points across the four milestones (20 + 25 + 25 + 30). Within each milestone, the same four questions are asked:

CriterionWhat earns the points
It runs (40%)Starts cleanly from the README steps and behaves as specified — routes answer, data persists, logins work
It is correct (30%)The week's concepts are used the way the course teaches them: REST shapes, middleware order, safe queries, hashed passwords, server-side checks
It is understandable (20%)Files organized by topic, sensible names, a README another student could follow
It is yours (10%)Your theme, your data, your decisions — and a reflection that sounds like someone who built it
Two hard rules.

First: never commit a secret — a password, key or connection string — to your repository; a leaked secret in a milestone is fixed by rotating it, not by deleting the file. Second: code you submit is code you can explain. Walking through your own app, out loud, is part of the final.

The Week 4 module page ends with a capstone walkthrough that assembles exactly this kind of app, piece by piece, mapped to the week each piece came from — build alongside it if you ever feel lost.
