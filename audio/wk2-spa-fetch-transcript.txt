Jordan: Here's what I don't get. My Vue app and my Express server are both JavaScript, and they're both mine. So why can't the page just reach over and read the books array sitting in the server's memory? Why all this fetching back and forth?
Alex: Because they are not one program. They are two separate programs that share no memory: two different computers in production, and even on your laptop, two processes that can't see into each other. Picture two kitchens whose cooks can never step into each other's room. The only way anything moves between them is a note passed across a counter. Your page's kitchen is the visitor's browser. The server's kitchen is the server process. The books array lives in the server kitchen's memory, and your page cannot reach in and grab it. A request is a note passed across. The response is the note that comes back.
Jordan: So the page has to ask, out loud, every single time?
Alex: To get fresh server data, yes. The page can render the array it already has again without fetching — but new data means a new note across the counter. Watch the section's example run. The page calls fetch with the address of the book API, which sends a GET request to the server. Fetch hands back a promise: a placeholder for a value that arrives later, because a network trip takes time your code cannot predict. When the answer comes back, its body is JSON text — plain characters that crossed the wire. The page converts that text into a JavaScript array, and only then can it render. That array holds two books: Dune by Frank Herbert, and Emma by Jane Austen.
Jordan: And the screen just follows from that array?
Alex: That is the whole idea of state. The state is the data the interface currently depends on — here, the list of books — and the screen is a function of the state. Change the state, re-render, and the screen is correct again. In the section's playground you type a title and an author, click Add book, and the list grows from two books to three. Nothing reloaded. The state changed, the rendering ran again, and the screen followed the data.
Jordan: In the playground, though, the new book just went into the page's own array.
Alex: It did, because that page has no server behind it, so it simulates the API with the same JSON. In the real app there is one extra beat at the front: the page sends the new book to the API, and the server assigns its id. The server, not the page, holds the authoritative copy. The page's state is a working copy. The Vue version shows the same split. When the app first appears, it fetches the books from the same API. When you add one, it pushes the book the server returns, with its real, server-assigned id, into the state. And nobody calls a render function, because that state is reactive: change it, and Vue re-renders on its own.
Jordan: At least errors are simple. If the server answers 404, fetch fails, and my error handling catches it. Right?
Alex: That is the silent-404 mix-up. Fetch only fails when no answer reaches your page: no connection, a server that isn't running, or a browser that blocks the answer. A 404 or a 500 still counts as a success as far as fetch is concerned, because an answer did arrive and the page can inspect it. That is why the section's pattern checks whether the response is okay, and turns a bad status into a thrown error itself.
Jordan: Different headache, then. I opened my page from a file, the browser blocked every call, and the console screamed about CORS. My server must be misconfigured.
Alex: That is the misconfigured-server mix-up. CORS is enforced by the browser, not by a crash on your server: when page and API live at different origins, the browser blocks the call unless the server explicitly opts in. An origin is a scheme, host, and port together, and yours did not match. The course's fix is to serve the page from the same Express app, so page and API share one origin and CORS never comes up.
