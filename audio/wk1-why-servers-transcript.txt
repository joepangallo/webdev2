Jordan: So Node is basically the browser's JavaScript moved onto a bigger computer, right? And a proper server takes one request, finishes it completely, then starts the next one. First come, first served, nothing overlapping.
Alex: Both halves of that are wrong. Start with the second, because one picture fixes it. Picture a coffee shop with a single barista. She is the only worker and can only do one thing at a time. But she never stands watching coffee slowly drip. She starts the drip, takes the next three orders, and hands the coffee over when ready. The barista is the JavaScript thread running your handlers: your JavaScript runs on a single thread, and the whole design is built around never making her watch something drip.
Jordan: But it is the same JavaScript, isn't it? The same language I used in the browser last term?
Alex: Same language, and the same V8 engine that runs it in Chrome — but a different runtime wrapped around it. The section runs one line of JavaScript through Node with no browser and no page in sight, and it prints 4. Node surrounds the engine with tools a browser would never allow: reading and writing files, listening for network connections. There is no page for the code to touch. The language carried over; the toolbox and the job are completely different.
Jordan: Still, one worker for a thousand visitors sounds like a disaster waiting to happen.
Alex: It would be, if servers spent their time working. Mostly they spend it waiting: waiting for the database to answer, waiting for a file to load. Watch the section's example, because the output looks wrong until you see the barista in it. The program prints 1. Then it calls setTimeout with a wait of zero milliseconds — zero — and the little function it registers, called a callback, will print 2. Then the program prints 3. The worker does run these instructions in order. The middle instruction registers the callback — it does not run it. So if you expected the print order to match the writing order, you would expect 1, 2, 3.
Jordan: And you actually see?
Alex: 1, 3, 2. setTimeout does not run its callback on the spot. It hands the waiting to the system and registers the callback for later, so the worker moves straight on and prints 3. Only when the current job finishes does the event loop — the barista's endless routine of check the line, run the next job, check again — pick the callback up from the event queue. So 2 prints last, even though its wait was zero milliseconds.
Jordan: So a request that needs the database works the same way?
Alex: Exactly the same. A visitor asks for a page that needs fresh data. Your handler asks the database, and instead of freezing, the worker serves other visitors while the database thinks. When the answer arrives, the callback joins the line and runs. And because the server runs your code for each request instead of serving one fixed file, the answers can be personal: one program reads each order and builds the response on the spot, so a greeting request carrying the name Ada gets Hello, Ada! and the same request carrying Grace gets Hello, Grace!
Jordan: Okay. Then to keep my code simple and in order, I will use the Sync versions, like readFileSync. The worker reads the file, then moves on. Clean and predictable.
Alex: That is the standing-and-watching mix-up. The Sync versions make the one worker stop and wait for the file, and while the worker waits, every other visitor waits too. In a request handler, use the non-blocking version, readFile: it starts the read and runs your callback when the file is ready. The Sync versions are fine in tiny scripts and startup code — never in a handler.
Jordan: Fine. But at least non-blocking means my code can never hold anyone up.
Alex: That is the busy-barista mix-up. Non-blocking only rescues waiting. If one order takes the barista five full minutes of continuous work — a huge calculation, say — everyone in line waits, because the worker is busy. Node is excellent at waiting-heavy work, which is most web work, and poor at long, unbroken calculations.
Alex: Quick check before you go. A program prints 1, sets a zero-millisecond timer to print 2, then runs a loop that takes two full seconds of pure calculation, then prints 3. What order, and when does 2 appear?
Jordan: 1, 3, 2, and 2 waits the whole two seconds. The callback can't run until the current job finishes, and a busy barista is still busy.
Alex: That's it. The code, the real output, and the barista are all in the section above — and the quiz at the end checks exactly this.
