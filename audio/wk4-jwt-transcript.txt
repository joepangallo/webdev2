Jordan: Okay, honest question. A JWT looks like total gibberish, just one long scrambled string. So if it is encoded like that, nobody can actually read what is inside it, right? The claims in there are basically hidden.
Alex: They are not hidden at all, and one picture fixes the model. Picture a signed letter mailed in a clear envelope. Anyone who handles it can read every word straight through the plastic. But the flap carries a wax seal made with a stamp only the sender owns. To change a word you'd have to open the envelope and break the seal, and nobody can make a fresh one without the stamp. That is the signed JWT in this demo. The writing is readable by everyone. The seal — the signature — is what proves who issued it and that nothing has changed since. It proves origin. It was never meant to provide secrecy.
Jordan: Wait — anyone can read it? Even me, with no secret?
Alex: Even you. The section has you prove it yourself in a little playground: split the token on its dots, decode the first two parts, and read them as plain JSON. No secret, no permission.
Jordan: So what does a real one say?
Alex: Follow the section's worked example. After login, the server builds a token with exactly three parts, joined by dots. Part one is the header, a small piece of JSON naming the signing algorithm: HS256. Part two is the payload — the claims, the facts the token asserts. In the demo those claims say the subject, sub, is user-42, the name is Ada, and the role is student. The library also stamps in iat, when the token was issued, and exp, when it expires — and in this token exp sits exactly 3,600 seconds, one hour, after iat. Part three is the signature, a value computed from the header, the payload, and a secret key only the server knows.
Jordan: And when Ada actually uses it?
Alex: Now watch the token come back. Ada's app presents it on a request to a protected route, in the Authorization header, introduced by the word Bearer — meaning whoever bears this token. The server does not remember Ada from login; it stored nothing. It verifies the signature and checks that the token hasn't expired. In the demo, verifying with the right secret hands back the payload — sub, name, role, iat, exp — and the route answers 200 OK and sends her grades. Verifying with a wrong secret fails on the spot, with the error invalid signature. And a request with no token, or a failed one, gets 401 Unauthorized and the error Missing or invalid token. Same route, same server. The only difference is whether a verifiable token arrived.
Jordan: All right, but here is a shortcut, then. If my server decodes a token and the payload looks right, that proves it is genuine, doesn't it?
Alex: That is the decode-means-valid mix-up, and it is backwards. Decoding is not verifying. Anyone can decode any token, including a forged one your server never issued. A decoded payload is just a claim written by whoever handed you the token. It only becomes trustworthy after the server verifies the signature with its secret. That verification, not the decoding, is what earns trust.
Jordan: Fine. The cancel-a-token mix-up: once I have a valid token it just keeps working, and if one leaks, the server can cancel it the way it cancels a session. Right?
Alex: Wrong on both counts, and the section is blunt about it: This demo keeps no revocation record. A copied token can work for the time remaining before expiry. A server that tracks revoked tokens can reject one sooner.
Alex: Quick check before you go. A classmate decodes your token, changes role from student to admin, re-encodes it, and sends it in. What happens?
Jordan: The signature was computed over the original payload, so the changed one fails verification — invalid signature — and the route answers 401. Reading it was free. Changing it is what the seal catches.
Alex: Exactly. The demo token, the decoding playground, and both responses are all in the section above — and the quiz at the end checks exactly this.
