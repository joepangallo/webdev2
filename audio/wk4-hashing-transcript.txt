Jordan: Okay, so when I sign up, the site hashes my password — encrypts it, basically — and stores the scrambled version. When I log in, it decrypts that and compares it with what I typed. Right?
Alex: That's the belief almost everyone starts with, and it has the wrong picture in one crucial way: there is no decrypt step, ever. Think of a fingerprint. A fingerprint on file can be checked against a new one to see if they match, but nobody can take that fingerprint and rebuild the finger. Hashing is like that: a one-way fingerprint of your password. Encryption is a different thing entirely — a locked box with a key. Whoever holds the key can open the box and get the original back. A hash has no key, and there is no way back.
Jordan: So what does the site actually keep, if it never keeps my password?
Alex: Follow the section's demo. Someone signs up with the password correct horse battery staple. The program makes a fresh random salt — random bytes, generated on the spot — and runs the password, mixed with that salt, through scrypt, a hash function that is deliberately slow. What gets stored is one single string in two parts: the salt, then a colon, then the hash. The stored value is the salt and the hash together, separated by a colon — one hundred sixty-one characters in all, and the console confirms exactly that. And notice what appears nowhere in it: the password itself.
Jordan: But at login, it can't compare what I typed against that string directly.
Alex: It never tries. It splits the stored string at the colon, takes the salt back out, and runs what you just typed through scrypt with that same salt. Then it compares the two fingerprints, using a function called timingSafeEqual, which takes the same amount of time whether the two differ in the first character or the last. The demo prints the verdicts: Right password accepted: true. Wrong password accepted: false — and the wrong password it tried was hunter2. Your real password was never stored, never recovered, never compared. Only fingerprints ever meet.
Jordan: Here's the part I don't buy. If the salt is just sitting there inside the stored value, out in the open, isn't that giving the game away? Shouldn't the salt be a secret too?
Alex: That's the secret salt mix-up, and no. The salt is not a secret, and it was never meant to be. Its job is uniqueness, not secrecy. The section's second example proves it: two users both choose hunter2, and because each one got a different random salt, their stored values come out completely different — the program literally prints Same stored value? false. An attacker holding a precomputed table of common passwords finds nothing to match, because every user's mixture is one of a kind.
Jordan: Fine, but the deliberate slowness still bugs me. SHA-256 is a hash too, and it's fast and modern. Why not use the fast one and keep logins snappy?
Alex: That's the fast hash mix-up. Speed is exactly what an attacker wants. If checking one guess costs almost nothing, a leaked table can be attacked with billions of guesses. Scrypt's slowness is the feature: every guess costs real time, and because each user has a different salt, the attacker pays that cost separately for every user. Slow once, for one honest login, is invisible. Slow a billion times is a wall.
