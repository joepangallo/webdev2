Jordan: So let me see if I have this right. When I log in, or add something to my cart, the server packs all of that into my cookie, and my browser carries it around. Every time I make a request, the cookie shows up with my cart inside it, and the server just reads everything back out.
Alex: That is the picture almost everyone starts with, and for the server-side sessions this course builds, it is exactly backwards. Think of a coat check at a theatre. You hand over your coat, and the attendant gives you a claim ticket with a number on it. The ticket is not your coat. It has no pockets and no sleeves, and it will not keep you warm. Your coat hangs in a back room, on a hook carrying that same number. The ticket does exactly one job: it points at your coat. A session works the same way. The browser holds only the ticket. The coat — your cart, your login, your visit count — stays with the shop, on the server.
Jordan: All right, but then how does the server keep track of me at all?
Alex: Watch the section's counting example. A visitor asks for the count page and the server answers Visit number 1. Behind the scenes, the server has started a brand-new session for this visitor, stored the count in it, and sent back a cookie holding nothing but that session's ID. The visitor returns, the browser presents the same cookie — the same ticket — and the server looks the ID up, finds the stored count, adds one, and answers Visit number 2. Once more, and it answers Visit number 3. Now the same visitor arrives with no cookie at all. No ticket, no lookup. The server cannot find any stored session, so it starts a fresh one, and the answer drops back to Visit number 1.
Jordan: So the count was never in my cookie to begin with.
Alex: Never. The section shows the two sides side by side. In the browser, the whole cookie is just the ticket: one ID, k-9-f-2-x. On the server, stored under that same ID, sits the real data: a visit count of 3, and a cart holding Dune and Emma. Only the ID and its signature travel in the session cookie. The handler reads the stored count and puts the new number in its response. And one honest detail the section flags: that short cookie is a simplification, so the ticket stays readable. The cookie you would actually see in your browser tools is named connect.sid, and its value is the session ID plus a signature — proof it really came from your server.
Jordan: Fine, but at least the server keeps all that session data safe in a database somewhere. It would survive a restart, surely.
Alex: Not by default, and that surprises people. Out of the box, the session package keeps the data in the server's own memory — its built-in store is even called the MemoryStore. Restart the server and every session evaporates: every visitor is logged out at once. Real sites plug in a store backed by a database instead. Until then, the server remembers only for as long as it keeps running.
Jordan: One more, then. Sessions are a login thing, right? Until I log in, there's no session and no cookie.
Alex: That's the login-only mix-up. A session isn't a login; it's a ticket for any visitor. The counter you just heard never asked anyone to log in, and it still climbed to 3. Logging in just hangs one more thing on your hook. And with the section's setup, the ticket is handed out on the very first response of a visit, before anything is stored at all — production apps often wait until something is actually stored, but the ticket itself was never about logging in.
Alex: Quick check before you go. When your third request arrives, what count does the server look up, and what does it send back?
Jordan: It finds 2 stored under my session ID, adds one, and sends back Visit number 3. The 3 was living on the server the whole time — my cookie only carried the ID.
