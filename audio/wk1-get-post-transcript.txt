Jordan: Honestly, when someone fills in my form and hits submit, I figured the data just lands in the request, all in one place, ready to read. And the route matched the address, so who cares whether it was a GET or a POST? The path is the path.
Alex: Both halves of that will bite you, and one picture explains why. Picture a request as an envelope with three places data can ride. The path is the address written on the front: it says where the envelope is going. The query string is extra writing on the outside of the envelope, right beside the address, so it shows up wherever the address does: the address bar, your history, server logs. And the body is the letter inside. It stays out of the address bar, but inside isn't the same as secret. Only HTTPS protects either one. One request, three parts of the envelope — and the verb decides which parts exist. A browser submitting a GET form puts its fields in the query string. A POST form sends its fields in the body, and its address can still carry a query string. And Express routes match on the verb and the path together — a GET to an address never triggers the POST handler for that same address.
Jordan: So when I search a site, my words are riding on the outside?
Alex: Exactly, and the section shows the handoff. The address asks for the search path and carries two pieces of data after the question mark: the term is vue, and the page is 2. Express turns that writing on the envelope into an object for your handler: term is vue, and page is the string 2 — in quotes, because everything in an address is text. If your code wants to do arithmetic with that page number, converting it is your job.
Jordan: And a POST form submission is the letter inside?
Alex: Watch the section's signup example run. The server console says Listening on port 3000. A form-style POST arrives carrying two pairs: a name, Ada, and a plan, free. The handler answers with JSON, and the answer says received, with the name Ada and the plan free inside it. Then a second client, a program instead of a browser, sends the same data as JSON, this time with the plan pro — and the same handler answers with pro. Two different formats went in, the same shape of answer came out, because the app switches on two translators — body-parsing middleware, one that turns form text into an object and one that does the same for JSON — and both deliver into the same part of the envelope: the request body. The section's book example shows the unpacking up close: the body text says the title is Dune and the author is Frank Herbert, with a plus sign standing in for the space — and the handler reads Frank Herbert, because that plus sign is just an encoded space.
Jordan: All right, but my first try at this, the handler printed the body and there was nothing there. So the form must not have sent anything.
Alex: That's the empty body mix-up, and the form is innocent. The body arrived as raw text, and raw text is all it stays until a translator turns it into an object. Forget the translators and the request body is undefined in Express 5. That is the single most common beginner bug with POST, and it is almost never the form's fault — it is a missing translator.
Jordan: Fine. At least every box on my form gets sent. My coupon box has an id, so it will show up.
Alex: That's the name mix-up. The browser packs each form control by its name attribute, and the name is the label on the package. A control with no name is left out entirely, no matter what the visitor typed into it. The section's playground flags the coupon field for exactly that: it has no name, so it never travels.
