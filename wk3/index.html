State on a Stateless Web: Cookies

Here is the problem this whole week solves. HTTP is stateless: it keeps no memory between requests. When your browser asks a server for a page, the server answers and then forgets you completely. Your next request — a second later, from the same browser — arrives as if from a total stranger. Nothing in HTTP itself connects the two requests.

That is a problem, because almost everything useful on the web needs memory. A shop has to remember what is in your cart while you keep browsing. A site has to remember that you already logged in, so it does not ask for your password on every single page. State is the word for that remembered information: facts about a visitor that carry across requests.

The coat-check ticket

Picture a coat check at a theatre. You hand over your coat, and the attendant hands you a small numbered ticket. The attendant does not remember your face, your name, or which coat is yours. Later, you hand back the ticket, and the number on it is enough to find your coat. Every visit works the same way: no memory, just a ticket presented each time.

The web works like that. The "ticket" is a cookie: a small piece of text — a name and a value, like visited=yes — that a server asks your browser to store. Your browser keeps it and then automatically sends it back with every later request to that site. The server never has to remember you. It just reads the ticket you present.

Example — the coat check, translated to the web:

At the coat checkOn the web
The attendant takes your coat and hands you ticket #42.The server's response carries a Set-Cookie header — "browser, store this."
You keep the ticket in your pocket.The browser stores the cookie, like visited=yes.

How a cookie round trip works

Two headers do all the work. A header is a line of extra information attached to an HTTP request or response, separate from the page itself:

  • Set-Cookie travels in a response. It is the server saying: "Browser, please store this."
  • Cookie travels in every later request. It is the browser saying: "Here is what you asked me to store."

Cookie attributes: the fine print on the ticket

A cookie is more than a name and a value. The server can attach attributes — extra instructions that control how long the cookie lives, where it is sent, and who is allowed to read it. You met one already: the Path=/ in the output above. Here are the ones that matter:

Cookies live on the visitor's machine — never trust them

A cookie is stored by the browser, which means the visitor can read it, change it, or delete it. Never store anything secret in a cookie, and never believe an important fact just because a cookie claims it. If a cookie says role=admin, anyone can edit it to say that. Next section you will see the fix: keep the real data on the server, and let the cookie carry only a meaningless ID.

Sessions and the File System

Cookies solved the memory problem, but badly: everything you want to remember has to fit in a small text string, on the visitor's machine, where the visitor can read and rewrite it. A shopping cart, a login, a half-finished form — none of that belongs out there. The fix is to flip the arrangement around. Keep the real data on the server, and let the cookie carry only one thing: an ID.

Sessions: the server remembers, the cookie points

A session is a chunk of data the server keeps about one visitor, stored under a random ID. The browser's cookie holds nothing but that ID — a long random string that means nothing on its own, like the number on a coat-check ticket. On every request, the server reads the ID from the cookie, looks up the matching data, and now it "knows" you: your name, your cart, your visit count.

The most common Express tool for this is the express-session package. Install it with npm install express-session, plug it in as middleware, and every request gains a req.session object you can read and write. Whatever you put there is remembered for that visitor:

The browser side holds nothing worth stealing or editing — k9f2x is meaningless on its own. Everything that matters, the visit count and the cart, sits in the server-side entry, and it only ever changes there.

A simplification, disclosed: the snapshot shortens the cookie to sid=k9f2x so the ticket idea stays readable. With the express-session setup above, the cookie you would actually see in DevTools is named connect.sid and looks like connect.sid=s%3A<id>.<signature> — the session ID plus a signature proving it came from your server. And because that setup uses saveUninitialized: true, the cookie is set on the first response of a visit — it does not wait until login, so a brand-new visitor gets a session (and a ticket) straight away.

One lookup, step by step

Step through a single request arriving at a server that uses sessions:

Browser sends request Cookie: session ID only Server looks the ID up Your code uses the data Response goes back

  1. The request arrives. Your browser asks for a page, like any HTTP request. Nothing about the request itself says who you are.

  2. The browser attaches the cookie automatically. Stored from an earlier Set-Cookie, the cookie carries only the session ID — a long random string. No name, no cart, no personal data travels with it.

  3. The session middleware looks the ID up. Before your route runs, express-session reads the ID and finds the data stored under it on the server. If there is no cookie, or the ID is unknown, it starts a fresh, empty session and arranges for a new ID cookie to be sent back.

  4. Your code sees req.session. The stored data appears as an ordinary object. Read from it, write to it — changes are saved under the same ID when the response is sent.

  5. The response goes back. It may carry a Set-Cookie header if a new session was created. The data itself never leaves the server; only the ticket does.

Cookie or session — which do you reach for?

Use a plain cookie for small, harmless preferences the visitor is allowed to see and change, like a theme choice. Use a session for anything that matters — logins, carts, progress — because the data stays on your server, under your control. Rule of thumb: if it would be a problem when a visitor edits it, it does not belong in a cookie.

Where do sessions live by default? In memory — and that matters

Out of the box, express-session keeps session data in the server's memory — its built-in store is called the MemoryStore. That is fine for learning and development, but restart the server and every session evaporates: all your visitors are logged out at once, and sessions cannot be shared between servers, because each server knows only its own. Real deployments plug in a session store backed by a database instead, so sessions get the same persistence as the rest of your data. Keep that in mind as you read on: "the server remembers" always quietly means "the server stored it somewhere."

Persistence in files

Sessions remember visitors while the server runs. But what about data that must survive the server stopping — notes, records, a list of books? That is persistence: storing data somewhere outside your program's memory, so it is still there when the program restarts. The simplest persistent home is a file: an ordinary named chunk of data on the computer's disk, like a text file on your own machine.

Node's built-in fs module (short for file system — the part of the operating system that organizes files) reads and writes files. Three functions cover the basics. The Sync versions work step by step, waiting for each write or read to finish before the next line runs, which keeps small examples easy to follow:

Real output — captured from running this code (Node v26.13.1). Two details to notice. The \n in each string is a newline — an invisible character meaning "start a new line" — which is why the file holds two lines, and why there is a blank line in the output: the file's text already ends with a newline, and console.log adds one more. And if you stop the program and run it again, the file is still on disk. That survival is the whole point of persistence.

Watch out for relative paths: when you pass a path like 'notes.txt' to an fs call, Node resolves it from the folder you were standing in when you ran node — your current working directory, the folder your terminal was in at launch — not from the folder the script lives in, so the same program can read different files depending on where you launch it. The fix is to build the path from the script's own folder instead, with path.join(__dirname, 'notes.txt') in CommonJS (the module system that uses require), where __dirname means "the folder this script lives in."

Why files stop being enough

Files are a fine first step, and for small tools they may be all you need. But watch what breaks as a site grows:

  • One server only. The file sits on one machine's disk. Run your app on two servers (which real sites do, so one can take over when the other is busy or down) and each has its own copy. A book added on server A is invisible on server B.
  • No sharing, no searching. A file is one long stretch of text. Finding "every book by Jane Austen" means reading the whole file and picking through it yourself, every time. Two parts of your program writing at once can tangle their changes together.
  • Fragile. One bad write — the program stops halfway through saving — can leave the file half-old, half-new, and unreadable. There is no undo and no safety net.

Example — two updates to one file at the same time, and one of them vanishes:

StepWhat happensbooks.json on disk afterwards
1Request A reads the file — 3 books — so it can add Dune Messiah.3 books
2Request B reads the same file — still 3 books — so it can add Persuasion.3 books
3A writes its copy back: its 3 books plus Dune Messiah.4 books, including Dune Messiah
4B writes its copy back: its 3 books plus Persuasion — overwriting A's file completely.4 books, including Persuasion — Dune Messiah is gone, and nobody saw an error

Both requests did everything "right." The file was simply never designed to be shared — each writer replaced the whole thing with the version it had read, and the later write silently erased the earlier one. That lost update is the sharing problem in miniature.

You need a program whose whole job is storing data well: keeping it safe, finding any piece of it quickly, and serving many programs at once. That program is a database, and it is where this week goes next.

Databases: Relational vs Non-Relational

A database is a program that stores data for other programs. Instead of your code shuffling text files around, you hand the data to the database and ask it questions: store this book, find every book by this author, change this price, delete that record. The database keeps the data safe on disk, organizes it so lookups are fast, and handles many programs asking at once. Your Express server is a client of the database — it asks, the database answers.

Databases come in two big families, and this week you will use one of each. They differ in how they picture your data.

Relational: data in tables

A relational database stores data in tables, which work like a careful spreadsheet. A table is a grid for one kind of thing — say, books. Each row is one item (one book). Each column is one fact about it (title, author), and every row has exactly the same columns.

Before any data goes in, you declare the table's schema: the plan that says what columns exist and what kind of value each holds (text, whole numbers, dates). The database then enforces the plan — a book with no title, or a price written as words, gets rejected. One column is special: the primary key, a value that uniquely identifies each row, like an ID number. No two rows share a primary key, so you can always point at exactly one row.

The word "relational" comes from tables being able to point at each other: an orders table can hold the primary key of a row in the customers table, linking the two. The language you use to talk to a relational database is SQL (Structured Query Language, usually pronounced "sequel" or spelled out). MySQL, which you will use in Section 3.5, is a relational database.

Example — authors and books as two linked tables:

The authors table — one row per author, and id is the primary key:

That author_id is the link in action: to find who wrote Emma, read its author_id — 2 — then look up row 2 in authors. The name itself is stored exactly once, in the authors table, and every book points at it.

Non-relational: data in documents

A non-relational database stores data as documents instead of rows. A document is a self-contained bundle of named fields and values — the same shape as a JavaScript object, or the JSON you have been sending all course. Documents that belong together live in a collection, the document world's rough equivalent of a table.

There is usually no strict schema. Two documents in one collection can carry different fields: one book can have a subtitle and another need not. Each document still gets a unique ID — in MongoDB, the database you will use in Section 3.4, it is stored in a field named _id and generated automatically if you do not supply one.

Nothing had to be declared in advance — the document simply carries the shape this particular book needs, and the next book's document may carry a different one.

When each one shines

Reach for relational when…

  • Every record truly has the same shape, and you want the database to enforce that shape.
  • Your data is full of connections — orders belong to customers, payments belong to orders — and you need those links to stay consistent.
  • Getting a number exactly right matters more than anything: money, inventory counts, grades.

Reach for documents when…

  • Records naturally vary — products where a shirt has sizes, a laptop has a processor speed, and a book has neither.
  • Your data already looks like JSON and you want to store it in the shape your code uses.
  • You are moving fast and the shape of your data is still changing week to week.

Neither family is "better." Banks and airlines run on relational databases; catalogs, content sites and activity feeds often run on document databases. Plenty of real systems use both. What matters is knowing which picture fits your data.

MongoDB CRUD with Node

Time to do it for real. MongoDB is the most widely used document database, and from Node you talk to it with its official driver package, mongodb. Three words of vocabulary before any code:

  • A database is one named store — ours is called bookstore. One MongoDB server can hold many databases.
  • A collection is a group of related documents inside a database — ours is books. Think "table," but for documents.
  • A document is one record: a JavaScript object, stored with a unique _id.

And one idea you already know runs this whole section: CRUD — the four basic things you can do to stored data. Create it, Read it, Update it, Delete it. You built all four against an in-memory list in Week 2. A database changes where the data lives, not what the four operations are.

Connect first

Install the driver with npm install mongodb. Then a program connects, picks a database and a collection, and works. Create: insertOne

{ acknowledged: true, insertedId: new ObjectId("6a05f1c2b8d4e5f60718293a") }

What comes back is a small report object from the driver. In prose: the driver reports acknowledged: true — the server confirmed the write — and hands back the new document's generated id in result.insertedId. That ID was added to your document as its _id; MongoDB generates one automatically whenever you do not supply it. insertMany does the same job for an array of documents at once.

Reading is a query: a description of the documents you want. The simplest query is an object naming fields and the values they must match — { author: 'Jane Austen' } means "documents whose author is Jane Austen," and {} (empty) means "all of them." find returns a cursor — a handle you walk through to get the documents — and calling .toArray() on it collects them into an ordinary array:

One habit to build now: findOne answers null when nothing matches — it does not throw an error. In a route, that null is your signal to answer 404, exactly as your Week 2 API did when a book ID was not in the array. Always decide what "not found" means before you write the happy path.

Update: updateOne with $set

Updating takes two arguments: a query that picks the document, and a description of the change. The change uses $set, which names the fields to change and leaves every other field alone:

What comes back:

{ acknowledged: true, matchedCount: 1, modifiedCount: 1, upsertedCount: 0, upsertedId: null }

That is the same edit your Week 2 API made with PUT /api/books/1 — the revised title, the author untouched. The driver's report tells you how many documents matched and how many were actually modified, so your code can check that the update found something. (updateMany applies the same change to every match.)

Delete: deleteOne

What comes back:

{ acknowledged: true, deletedCount: 1 }

One query, one document gone. The report's deletedCount tells you whether anything was actually deleted — 0 means your query matched nothing, which usually means a typo worth knowing about. deleteMany removes every match, and deserves a careful look at the query before you run it.

From driver calls to routes

So far the driver calls have lived in a standalone program. In your Week 2 API they live inside route handlers, and the route's job is translating between HTTP and the database: an HTTP request comes in, a driver call goes out, and the result becomes an HTTP response. The list route is the direct swap — run find().toArray(), then answer with the documents as JSON using res.json(...), which sends a value back as a JSON response:

Reading one book adds a translation step. An id arrives in the URL as a string — every URL is text — but MongoDB stores _id values in its own type, ObjectId, so you convert the string with new ObjectId(id) before you search. That conversion sits in its own try/catch (code that tries a step and catches an error it throws, instead of crashing) because an invalid id string makes new ObjectId(...) throw — and a bad id is the visitor's mistake, not the database's:

Notice that one route gives three different failure answers, because three different things went wrong. "Bad id" is 400 — the request itself was malformed. "Not found" is 404 — the request was fine, but no such book exists, which is why the handler checks for the null that findOne returns. "Database down" is 500 — your server failed — and the handler does not answer that one itself: passing the error on with next(err) hands it to the error-handling middleware from Week 2, which sends the 500. Keeping those three apart is what makes an API's answers mean something to whoever called it.

What comes back from a write, like an INSERT — no rows at all, just a short report. The two fields you will actually read are affectedRows (how many rows the write changed) and insertId (the AUTO_INCREMENT id the new row was given — here, a fourth book going in):

{ affectedRows: 1, insertId: 4 }

From Node, the package is mysql2 — install it with npm install mysql2 — and its /promise version lets you await each query. Here is the full CRUD cycle. Read the queries closely: none of them glue values into the SQL text. Wherever a value belongs, the SQL has a ? instead, and the value travels separately, in an array:

Notice the pattern in lines like const [rows] = await db.execute(...): mysql2 hands back a pair, [rows, fields] — the rows you asked for, plus a description of the columns (the fields) — and the destructuring keeps only the first item, the rows. And in a real Express server, that connection — or better, a connection pool, a small set of reusable connections the driver manages for you — is created once, when the server starts, and shared by every request; you never open a new connection per request, because opening one is slow work that only needs doing once.

Those ? marks are called placeholders, and the style is called a parameterized query — the values are parameters, passed alongside the SQL instead of inside it. This is not a style preference. It is one of the most important habits in this course, for two reasons:

  • Correctness. The driver handles all the quoting and escaping for you. An author named O'Brien — with an apostrophe that would break a hand-built SQL string — just works.
  • Security. Because the values never become part of the SQL text, a value can never be mistaken for SQL. If you glue user input into a query string instead — 'SELECT ... WHERE id = ' + req.params.id — a hostile visitor can type text that changes what the query does, reading or deleting data they should never touch. That attack has a name, SQL injection, and Week 4 takes it up properly. Placeholders shut it down: whatever the visitor types is treated as data, never as instructions.
Never glue user input into a SQL string

Every value that comes from a request — a route parameter, a form field, a JSON body — goes into a query through a ? placeholder. No exceptions, even for values that "look like numbers." The day you make an exception is the day the input is not what you assumed.

Validation, Consistency and Configuration

Your data can now live in cookies, sessions, files and two kinds of database. This last section is about keeping that data good — because a database faithfully stores whatever you hand it, including nonsense. Programmers summarize it as garbage in, garbage out: if bad data gets in, every answer built on it is bad too, no matter how correct the rest of your code is.

Validate on the server — never trust the browser alone

Validation means checking data against your rules before you accept it: is this field present? Is it the right type? Is it a sensible length? You met browser-side validation in Web Dev I — required, minlength, input types — and it is genuinely useful: it answers instantly and politely, while the visitor is still on the page.

But browser checks are a courtesy, not a guard. Your server does not only hear from your tidy web page. Anyone can send your API a hand-made request with curl, skipping your form — and its JavaScript — entirely. Worse, everything arriving in a request was assembled on someone else's machine: bodies can be edited, cookies rewritten, fields deleted. So the rule is absolute: every rule that matters is checked again on the server, at the moment the data arrives, before it touches your database. The browser check is for the visitor's convenience. The server check is for your data's survival.

Consistency: one fact, one home

Validation keeps bad values out. Consistency is the companion idea: the data you have should agree with itself. The simplest way to protect it is one source of truth — each fact is stored in exactly one place, and everything else looks it up from there.

Suppose every order stores a copy of the customer's email address, and the customer changes their email. Now you must find and fix every copy. Miss one, and your database disagrees with itself: two places claim to know the email, and they say different things. Which is right? Nobody knows — that disagreement is inconsistency. Relational databases fight this with the links from Section 3.3: the order stores only the customer's primary key, the email lives once in the customers table, and a change happens in exactly one place. Document databases make the same trade differently, often copying a fact into a document on purpose for speed — but then the copying is a deliberate choice with a plan for updates, never an accident.

Example — an author's name, stored twice vs stored once:

Stored twice: the author's name lives in the books table and is copied into a staff-picks list. The name is corrected from J. Austen to Jane Austen in the books table — but the copy is missed, and now the site disagrees with itself:

Where you lookTitleAuthor shown
Books tableEmmaJane Austen (corrected)
Staff-picks listEmmaJ. Austen (the stale copy)

Stored once: the name lives in exactly one row — the authors row, as in Section 3.3 — and everything else points at it. The books row keeps only the author's id, and the staff-picks entry keeps only the book's id:

Where it livesWhat is stored
Authors table, one row{ id: 2, name: 'Jane Austen' } — the author's name lives only here
Books table, one row{ id: 2, title: 'Emma', author_id: 2 } — the book points at the author, never copies the name
Staff-picks list, one entry{ book_id: 2 } — the pick points at the book, and the name is looked up through it: book, then author_id, then the authors row

With one home for the fact, the correction happens once, in the authors row, and every page that looks the book up — following its author_id — shows the new name. There is no second copy to miss.

The same principle runs your whole week. The session ID is a pointer to one server-side record, not a copy of it. The book's title is changed with one $set or one UPDATE, in one row or document. Whenever you catch yourself storing the same fact twice, stop and ask which copy is the truth — and how the other one gets updated.

Configuration: settings live outside the code

Last piece. Your programs need settings that change from machine to machine: which port to listen on, where the database lives, what the session secret is. Hard-coding them means editing code for every deployment — and it means secrets sitting in your source. The standard home for settings is environment variables: named values provided by the machine or shell that runs your program, which Node reads through process.env:

While developing, you collect these in a .env file — a plain text file in your project folder, one NAME=value per line, loaded when the app starts (commonly with the dotenv package: npm install dotenv, then require('dotenv').config(); at the top of your entry file):

Secrets never go in code, and never in Git

A password typed into a .js file gets copied everywhere the code goes — including GitHub, where automated scanners find committed secrets within minutes and strangers use them. So: secrets live in environment variables and the .env file, the .env file is listed in .gitignore so Git never commits it, and a secret that has been committed is treated as leaked — change it, don't just delete the line. Week 4 returns to this when sessions and logins make the stakes real.

A .gitignore file — a plain list of names Git should leave out of commits — keeps node_modules and .env out of Git: you commit a .env.example file with the variable names and placeholder values, never the real values.

Week 3 Review

One thread runs through the whole week: HTTP forgets, so you build memory in layers. A cookie is a ticket the browser presents. A session keeps the real data on the server, behind an ID on that ticket. Files make data survive a restart, and databases make it survive well — searched, shared and guarded — in two shapes, tables and documents, each with the same four CRUD operations. Validation, consistency and configuration are how you keep all of it trustworthy.
